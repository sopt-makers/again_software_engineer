# 1장. 프로그래머에서 이제는 엔지니어로

## 핵심 요약

- 소프트웨어 엔지니어는 코드 작성뿐 아니라 요구사항, 설계, 테스트, 배포와 운영을 연결해서 생각한다.
- 학습 경로보다 중요한 것은 실무에 필요한 역량의 빈틈을 인식하고 계속 채우는 태도다.
- 구현 전에 실제 문제와 제약을 이해하고, 기존 해결책과 현재 방식의 근거를 확인한다.
- 조기 피드백으로 수정 비용을 줄이고, 다음 개발자가 이해하고 유지보수할 수 있는 결과물을 남긴다.

## 1. 프로그래머에서 엔지니어로 관심의 범위 넓히기

책은 프로그래머·코더, 개발자, 소프트웨어 엔지니어를 관심의 범위로 구분한다. 이는 책이 제시하는 설명이며, 실제 직함만으로 사람의 역량을 판단한다는 뜻은 아니다.

| 구분 | 책에서 강조하는 관심의 범위 |
| --- | --- |
| 프로그래머·코더 | 특정 언어나 프레임워크를 사용해 코드를 작성하고 기능을 구현한다. |
| 개발자 | 소프트웨어 전달의 큰 그림을 이해하며 여러 기술과 도메인을 다루고 동료의 성장을 돕는다. |
| 소프트웨어 엔지니어 | 전체 개발 수명 주기에 공학적인 판단을 적용하고 확장성, 신뢰성, 효율성, 보안을 고려한다. |

문법적으로 올바른 코드를 작성하는 것만으로는 제품의 성공을 보장할 수 없다. 고객에게 필요한 기능인지, 변경을 감당할 구조인지, 운영 환경에서도 의도대로 동작하는지까지 살펴야 한다.

또한 규칙을 아는 것에 그치지 않고, 특정 상황에서 왜 그 규칙이 유효한지와 언제 유연하게 적용할지를 이해해야 한다. 관심이 코드 한 부분에서 제품의 전체 생애로 넓어지는 것이 이 장의 출발점이다.

## 2. 기본기를 반복해서 다져야 하는 이유

책은 운동선수들이 기초 동작을 계속 연습하는 것처럼 소프트웨어 엔지니어도 기본 원칙을 숙달해야 한다고 설명한다.

실무의 기본기는 언어 문법에 한정되지 않는다.

- 다른 사람이 작성한 코드를 읽고 의도를 파악하는 능력
- 다음 사람이 이해하기 쉽게 코드를 작성하는 능력
- 동료와 요구사항 및 설계 판단을 공유하는 능력
- 모르는 것을 인정하고 필요한 지식을 찾아 배우는 태도
- 새로운 기술을 익히고 기존 기술의 변화에 적응하는 능력

실무에서는 대부분 기존 코드 안에서 일한다. 따라서 낯선 코드와 모호함을 받아들이는 능력도 필요하다. 모든 코드를 완전히 이해한 뒤에야 수정할 수 있는 것은 아니며, 작업에 필요한 이해를 점진적으로 쌓아야 한다.

최신 기술을 익히는 것만큼 소통과 협업 같은 지속적인 역량에도 투자해야 한다.

## 3. 학습 경로와 실무 역량의 차이

### 다양한 경로에는 서로 다른 장단점이 있다

| 경로 | 특징 | 보완할 부분 |
| --- | --- | --- |
| 대학의 컴퓨터 과학 교육 | 알고리즘, 언어, 컴파일러, 운영체제 등 이론적 토대를 다룬다. | 장기간 운영되는 제품과 대규모 기존 코드의 현실을 경험할 기회가 부족할 수 있다. |
| 부트캠프 | 특정 언어와 프레임워크를 짧은 기간에 집중적으로 배운다. | 기술의 변화에 대응할 기본 원리와 폭넓은 실무 역량을 추가로 쌓아야 한다. |
| 독학 | 관심과 속도에 맞춰 자료를 선택할 수 있다. | 자료의 품질을 판단하고 학습을 지속할 자기주도성이 필요하다. |

책이 강조하는 것은 특정 경로의 우열이 아니다. 문제 해결, 실험, 창의력을 발휘하며 배운 기술을 실제 제품에 연결할 수 있는지가 중요하다.

### 교육용 프로젝트와 실제 제품은 다르다

교육용 프로젝트는 작고, 기간이 짧으며, 기술 부채가 없는 상태에서 시작하는 경우가 많다. 반면 실무에서는 이전 개발자의 결정, 기존 사용자, 운영 데이터, 다른 팀과의 의존 관계를 고려해야 한다.

실제 코드는 저장소에서 평가받기 위한 결과물에 그치지 않는다. 사용자가 의존하는 운영 환경에서 사업적 가치를 제공한다. 제품이 가치를 제공하는 동안 개선과 유지보수도 계속된다.

따라서 개발을 끝이 정해진 과제처럼 보기보다 지속적으로 관리하는 제품으로 바라볼 필요가 있다.

## 4. 게으른 프로그래머 정신: 불필요한 일을 줄이기

게으른 프로그래머 정신은 효율성을 지향하는 태도다. 구현을 시작하기 전에 생각하고 조사하는 시간이 이후의 불필요한 작업을 줄일 수 있다.

문제를 마주하면 다음을 확인한다.

1. 이미 해결된 문제인가?
2. 현재 코드나 언어의 내장 기능으로 해결할 수 있는가?
3. 라이브러리나 프레임워크에 적합한 기능이 있는가?
4. 선택한 알고리즘과 구조가 예상 규모에 적절한가?

무차별 대입 방식에서 출발할 수는 있지만, 그대로 최종 설계로 굳히기 전에 개선할 여지가 있는지 살펴야 한다. 최선·평균·최악의 경우와 계산 비용에 대한 이해가 선택을 돕는다.

### 책의 사례: 대문자 변환

저자는 청구지 주소를 대문자로 변환하는 작업을 맡았다. 기존의 자체 함수는 인자가 많고 복잡해서 이해하는 데 상당한 시간이 필요해 보였다.

언어가 제공하는 기능을 조사한 결과 내장 대문자 변환 함수를 발견했고, 이를 활용했다. 기존 함수가 있다는 이유만으로 그대로 따르기보다 더 간단한 해결책을 찾은 것이다.

이 사례는 기존 코드를 무조건 교체하라는 뜻이 아니다. 현재의 선택지가 무엇인지 먼저 확인하면 불필요한 구현과 분석을 줄일 수 있다는 교훈이다.

## 5. 새로운 시각의 가치

새로운 구성원은 과거의 결정에 덜 얽매여 있다는 장점이 있다. 익숙한 팀원이 지나치는 비효율을 발견하고, 당연하게 여긴 전제에 질문할 수 있다.

### 책의 사례: 야간 배치 처리

고객과 처리 대상이 늘어나면서 순차적인 배치 작업이 밤사이에 끝나지 않게 되었다. 저자는 각 처리 대상이 서로 의존하는지 물었다.

개별 작업은 독립적이었고 마지막 집계만 필요했다. 이를 바탕으로 여러 작업 프로세스가 각각 처리한 결과를 집계 큐에 넣는 병렬 처리 방식을 제안했다.

개선의 계기는 작업 사이의 의존 관계를 다시 확인하는 질문이었다. 과거에 적절했던 방식도 규모나 조건이 달라지면 재검토해야 한다.

질문할 때는 이전 개발자를 비난하기보다 당시 맥락을 배우려는 태도를 취한다. 이상해 보이는 구조에도 현재는 드러나지 않는 이유가 있을 수 있다.

## 6. 성급한 해결책과 과도한 설계 경계하기

### 기능 요청의 이면에 있는 문제 확인

고객이 특정 기능을 요청했다는 것은 하나의 해결책을 제시했다는 의미일 수 있다. 예를 들어 테이블을 스프레드시트로 내보내 달라는 요청을 받으면, 데이터를 왜 외부로 옮겨야 하는지부터 물어볼 필요가 있다.

기존 시스템의 숙련 사용자는 중요한 지식을 제공하지만, 익숙한 업무 방식에 영향을 받을 수도 있다. 따라서 새 기술로 기존 시스템의 동작을 그대로 복제하는 것이 실제 문제를 해결하는지 검토해야 한다.

### 다섯 번의 왜

표면적인 증상에서 근본 원인으로 내려가기 위해 답변에 다시 ‘왜?’를 묻는다.

책의 로봇 사례에서는 작동 중단, 퓨즈 단선, 베어링 윤활 부족, 오일 순환 문제, 흡입구 막힘을 따라가며 필터 부재라는 원인에 도달한다. 단순히 퓨즈만 교체하면 같은 문제가 반복될 수 있다.

중요한 것은 정확히 다섯 번 질문하는 형식이 아니라, 답변의 근거를 확인하며 원인을 깊이 이해하는 것이다.

### 미래의 필요를 지나치게 가정하지 않기

가능한 미래를 모두 대비하려고 하면 쓰이지 않을 코드와 추상화가 쌓인다. 확장성은 중요하지만 모든 제품이 극단적인 규모를 감당해야 하는 것은 아니다.

현재 문제, 예상되는 변화, 제약을 함께 보면서 실용적인 해결책을 선택해야 한다.

## 7. 문제 발견과 피드백을 앞당기기

운영 중 발견한 문제는 사용자 피해, 데이터 복구, 긴급 대응과 팀 간 조율까지 수반할 수 있다. 개발 직후 발견하면 작업 맥락이 남아 있고 테스트 데이터를 복원하기도 쉬워 수정 부담이 줄어든다.

| 실천 | 앞당기는 피드백 |
| --- | --- |
| 짝 프로그래밍 | 구현 중에 설계와 코드를 함께 검토한다. |
| 지속적인 테스트 | 변경 직후 기대 동작과 오류를 확인한다. |
| 지속적 통합(CI) | 자주 통합하며 충돌과 통합 문제를 발견한다. |
| 지속적 전달(CD) | 전달 과정과 환경 차이의 문제를 더 일찍 확인할 기회를 만든다. |
| 개발 과정의 보안 검토 | 출시 전에 취약한 설계와 구현을 발견한다. |

다만 요구사항을 잘못 이해한 문제는 기술적인 검증만으로 발견하기 어렵다. 책은 비슷해 보이는 도메인 용어도 실제로는 다른 개념일 수 있음을 강조한다. 용어집과 대화를 통해 의미를 맞추는 일이 필요하다.

## 8. 소프트웨어의 황금률

다음 개발자와 미래의 자신이 어떤 코드와 문서를 받기를 원하는지 생각한다.

- 의도가 드러나는 이름과 읽기 쉬운 구조를 남긴다.
- 문서를 코드의 변화에 맞춰 갱신한다.
- 복잡한 관계를 설명하는 도식을 남긴다.
- 질문에 답하고 동료가 이해할 수 있도록 돕는다.

코드는 컴퓨터를 실행시키는 수단인 동시에 다른 개발자와 소통하는 수단이다. 동료의 작업을 쉽게 만드는 행동도 엔지니어링의 일부다.

## 실천

- 새 작업을 받으면 구현 전에 문제, 실제 필요, 기존 해결책, 제약을 적어본다.
- 익숙한 방식 하나를 골라 도입 이유와 현재도 유효한 조건을 확인한다.
- 사용하는 추상화 계층 바로 아래의 동작 원리를 공부한다.
- 경험 많은 동료에게 판단 기준과 더 일찍 배웠으면 좋았을 지식을 묻는다.
