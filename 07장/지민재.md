## 7장 핵심 정리

좋은 UI는 단순히 보기 좋은 화면을 만드는 것이 아니라, **사용자가 소프트웨어를 쉽고 편리하게 사용할 수 있도록 설계**하는 것이다. 이를 위해서는 개발자의 관점이 아닌 실제 사용자의 입장에서 사용 목적과 환경을 이해하고, 사용성과 접근성을 고려해야 한다. 또한 국제화와 지역화도 초기 설계 단계부터 고려하면 다양한 언어와 문화권의 사용자에게 적합한 서비스를 제공할 수 있다.

UI를 설계할 때는 사용자가 기능을 쉽게 배우고 효율적으로 사용할 수 있어야 하며, 오랜만에 사용하더라도 기능을 기억하고 쉽게 찾아낼 수 있어야 한다. 이를 위해 **대비, 반복, 정렬, 근접성**이라는 디자인 원칙을 활용해 정보를 명확하게 전달하고 화면의 일관성을 유지하는 것이 중요하다.

또한 좋은 UI는 사용자가 실수하지 않도록 돕고, 오류가 발생했을 때 문제를 이해하고 해결할 수 있도록 안내해야 한다. 특히 데이터 삭제처럼 되돌리기 어려운 작업은 명확한 경고와 확인 절차를 제공해야 한다. 결국 좋은 UI 설계란 화면을 아름답게 만드는 데 그치지 않고, **사용자가 기능을 올바르게 이해하고 원하는 작업을 쉽고 안전하게 수행할 수 있도록 돕는 것**이다.

## 인상 깊었던 부분

> UI는 UX의 실체이다. 거의 모든 사용자에게 UI가 곧 애플리케이션 그 자체라는 점을 잊지 말자. UI 설계는 단순히 겉모습을 매끄럽게 꾸미는 것 이상의 일이다. 대상 사용자가 애플리케이션을 쉽게 쓰도록 만드는 것이 핵심이다.

→ 처음에는 UI 설계가 화면을 만드는 디자이너에게 가장 중요한 내용이라고 생각했다. 물론 FE 개발자에게도 중요하겠지만, BE 개발자에게도 얼마나 중요할지 궁금했다. 그런데 책을 읽다 보니 AI를 활용해 하나의 애플리케이션을 처음부터 끝까지 개발하는 시대에는 FE, BE 구분 없이 개발자라면 UI 설계의 기본을 알아야 하지 않을까 하는 생각이 들었다. (그리고 읽다 보니 내게 가장 필요한 장이라고 생각이 들기도 했다… 기억해야 할 게 많다)

특히 UI가 UX의 실체라는 표현이 인상 깊었다!! 사용자에게는 UI가 곧 애플리케이션 그 자체일 수 있다는 점을 잊지 말아야겠다...🧎🏻‍♀️

> 접근성, 사용성, 포용성은 서로 다르면서도 연결된 개념으로, 배경이나 능력과 상관없이 다양한 사람이 제품을 사용할 수 있게 만드는 것이 목표다. 접근성(accessibility)은 a11y, 지역화(localization)는 L10n, 국제화(internationalization)는 i18n이라고 줄여서 표기한다.

→ 평소 다국어 처리를 `i18n`이라고 자연스럽게 부르고 있었는데, 접근성과 지역화도 숫자 약어로 표현한다는 것을 새롭게 알게 되었다!! 신기하다. 단순히 기술적인 용어로만 알고 있었는데, 다양한 사용자가 제품을 이용할 수 있도록 한다는 맥락에서 함께 다루어진다는 점이 흥미로웠다.

> 능력이 제각각인 사용자, 하드웨어나 소프트웨어 사양, 인터넷 연결 품질이 다른 환경, 그리고 다양한 지역적 특성을 고려해야 한다.

→ 평소 스크린 리더나 접근성 같은 부분을 조금 소홀하게 생각했던 것 같아 반성하게 되었다. 마우스를 사용하는 것이 당연하다고 생각했는데, 키보드의 탭 키만으로 화면을 탐색하는 사용자도 있을 수 있겠지! 내가 익숙한 사용 방식이 모든 사람에게 당연한 것은 아니라는 점을 기억해야겠다.

> 소프트웨어에 접근하기 좋게 만드는 것은 단순히 장애가 있는 사람뿐만 아니라 모든 사용자에게 도움이 된다. 휠체어를 위해 만든 경사로가 여행 가방을 끄는 사람에게도 유용한 것과 마찬가지다.

→ 비유가 정말 인상 깊었다!! 접근성을 특정 사용자만을 위한 기능으로 생각했는데, 접근성을 높이는 설계가 다른 사용자에게도 도움이 될 수 있다는 점을 쉽게 이해할 수 있었다. 중요한 것은 일부 사용자를 위한 기능이라고 한정하지 않고, 더 많은 사람이 편리하게 이용할 수 있도록 만드는 것이라는 생각이 들었다.

> 인터페이스를 사용할 대상과 환경을 이해하지 못하면 사용성 높은 애플리케이션을 만들 수 없다. 사용자를 지나치게 일반화하는 것은 위험하므로 항상 가정을 의심해야 한다.

→ 사용자가 어떨 것이라고 추측하면서 개발하면 안 된다는 점에서 반성하게 되었다. 사용자의 세대나 신체적 특성 등을 보고 행동을 일반화하기보다, 실제로 어떻게 서비스를 이용하는지 파악하려는 노력이 필요하다.

그렇다면 기획 단계에서 사용자 페르소나를 설정하더라도 그 안의 모든 사용자가 같은 환경과 특성을 가지고 있는 것은 아닐 것이다. 주요 사용자를 정의하는 것과 그 안에서 다양한 사용자를 고려하는 일 사이에서 어떤 균형을 잡아야 할지 궁금해졌다... 🤔

> 실제 고객 중 대표성을 가진 사람을 선정해서 그들이 애플리케이션을 사용하는 모습을 곁에서 지켜보자.

→ 이 부분을 읽으면서 UT가 중요하다는 생각이 들었다!! 실제로 그로잉팟 프로젝트의 MVP 구현 단계에서 합숙하며 UT를 진행한 경험이 있다.

당시 졸업까지의 로드맵을 노드와 카드 형태로 보여주는 페이지가 있었는데, 팀원들은 기획부터 몇 주간 해당 화면을 봐 왔기 때문에 사용 방법을 이해하는 데 어려움이 없었다. 하지만 UT를 진행하자마자 사용자가 페이지에 들어온 뒤 어떻게 시작하고 사용해야 할지 모르겠다고 이야기했다.

우리는 우측 하단에 도움말 버튼을 만들어 두었지만, 사용자는 처음 페이지에 들어왔을 때 화면 자체가 모호하게 느껴져 도움말을 찾아볼 생각조차 하지 못했다. 그래서 최초 진입 시 안내 팝업을 띄우고, 슬라이드를 넘기며 사용 방법을 확인할 수 있도록 변경했다. 이후에도 다시 확인할 수 있도록 기존 도움말 버튼은 유지했다.

이 경험을 통해 우리가 익숙하게 사용하는 화면이라고 해서 사용자도 쉽게 이해할 수 있는 것은 아니라는 점을 알게 되었다. 실제 사용자의 반응을 확인하지 않았다면 놓쳤을 문제였기 때문에 UT의 필요성을 체감할 수 있었다!!

> 이쯤 되면 사용성의 여러 요소(학습 용이성, 효율성, 기억 용이성, 발견 용이성, 오류 처리, 사용자 만족도, 접근성) 중 어디에 집중해야 할지 궁금할 것이다. 모든 요소를 극대화하려고 달려들지 말고 가장 중요한 질문을 던져야 한다. "이 애플리케이션이 어떻게 사용될 것인가?"

→ 사용성을 높이기 위해 모든 요소를 무조건 극대화해야 하는 것은 아니라는 점이 인상 깊었다. 매일 사용하는 업무용 애플리케이션이라면 효율성이 중요하겠지만, 가끔 사용하는 앱이라면 기능을 쉽게 발견하고 기억할 수 있도록 하는 것이 더 중요할 수도 있다. 결국 애플리케이션의 목적과 사용 맥락을 먼저 파악해야 한다는 점을 기억하고 싶다!! (영원히 기억을 해)

> 사용자에게 맥락 정보를 제공하는 것 외에도, 애플리케이션은 사용자가 실수를 만회할 수 있게 해야 한다. 실행 취소나 되돌리기 기능을 제공하는 것은 사용자가 마음껏 탐색할 수 있게 만드는 핵심 요소다. 실수를 되돌릴 수 없다면 사용자는 새로운 시도를 하지 않을 것이다.

→ 개발자가 예상할 수 있는 오류라면 미리 입력값을 검증하거나 안내 메시지를 제공해 대응할 수 있다. 하지만 미처 예상하지 못한 오류가 발생하면 어떻게 해야 할까? 모든 오류를 미리 예측할 수는 없으니, 발생한 오류를 개발자가 파악하고 대응할 수 있는 방법도 필요할 것 같다.

예를 들어 오류가 발생했을 때 사용자가 해당 내용을 전달할 수 있는 기능이 있다면, 개발자가 문제를 더 빠르게 파악하는 데 도움이 되지 않을까? 오류가 발생했을 때 사용자에게 복구 방법을 제공하는 것뿐만 아니라, 개발자가 오류를 발견하고 개선할 수 있도록 하는 방법도 고민해 보고 싶다......
