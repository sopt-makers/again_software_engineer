# 8장. 다양한 데이터 기술을 적절하게 사용하는 방법

## 핵심 요약

- 데이터는 수집, 저장, 변환, 조회와 이전까지 전체 수명 주기를 고려해 다뤄야 한다.
- 데이터의 구조와 접근 패턴, 일관성 요구와 팀의 역량에 따라 형식, 저장소와 추상화 수준을 선택한다.
- 트랜잭션, 연결 관리와 캐시는 성능뿐 아니라 실패와 데이터 무결성을 함께 고려해야 한다.
- 필요한 데이터만 읽고 실제 실행 계획과 관측 자료로 병목을 확인한 뒤 최적화한다.
- 데이터 증가와 이전은 검증·동기화·복구를 포함해 계획하며, 가상의 미래보다 현재 문제와 확인된 요구에 맞춰 발전시킨다.

## 1. 데이터는 데이터베이스보다 넓은 문제다

애플리케이션은 데이터를 수집하고 저장하며 변환한 뒤 사용자에게 의미 있는 형태로 제공한다. 데이터베이스 선택만으로 데이터 설계가 끝나는 것은 아니다.

자료형과 형식, 개체 간 관계, 조회 방식, 무결성, 성능과 스키마의 변화까지 연결해서 생각해야 한다. 개발 환경의 적은 데이터에서는 문제가 드러나지 않아도 운영 규모와 동시 접근에서는 전혀 다른 결과가 나올 수 있다.

데이터는 애플리케이션 구현보다 오래 남을 수 있다. 코드를 바꾸는 것과 이미 저장한 정보를 바꾸는 것의 비용과 위험은 다르다.

## 2. 데이터 형식을 선택하는 기준

- 사람이 읽고 편집하는가, 시스템이 교환하고 처리하는가?
- 데이터의 크기와 처리 속도는 얼마나 중요한가?
- 어떤 소비 시스템과 호환되어야 하는가?
- 구조가 얼마나 중첩되거나 자주 바뀌는가?
- 스키마와 값의 검증이 필요한가?

한 시스템에서도 API, 설정, 다운로드는 서로 다른 요구를 가질 수 있다. 모든 데이터에 같은 형식을 적용할 필요는 없다.

## 3. 정형 데이터와 비정형 데이터

| 구분 | 정형 데이터 | 비정형 데이터 |
| --- | --- | --- |
| 구조 | 미리 정의한 필드와 관계 | 정해진 테이블 구조로 표현하기 어려운 내용 |
| 예 | 사용자 속성, 주문, 재고 | 자유로운 텍스트, 이미지, 오디오, 문서 |
| 장점 | 규칙 검증과 정밀한 검색에 유리 | 풍부한 맥락과 다양한 콘텐츠를 보존 |
| 과제 | 필드 변경에 스키마와 코드 수정이 필요 | 검색, 해석과 대용량 저장에 별도 방법이 필요 |

책의 고객 피드백 사례는 원문 텍스트에서 감성과 키워드를 추출하고 원본과 함께 저장한다. 비정형 콘텐츠를 버리지 않으면서 구조화한 정보를 조회에 활용하는 방식이다.

데이터 형식과 정형성은 같은 분류가 아니다. JSON으로 표현한다고 자동으로 비정형 데이터가 되는 것은 아니다. 실제로 어떤 구조와 검증 규칙을 사용하는지 봐야 한다.

## 4. 일반적인 데이터 형식

| 형식 | 특성 | 적합한 사용 | 주의할 점 |
| --- | --- | --- | --- |
| JSON | 객체와 배열 중심, 언어 독립적인 교환 형식 | API, 문서형 데이터 | 기본 날짜 타입과 주석이 없으며 이진 데이터 표현에 별도 인코딩이 필요 |
| XML | 요소·속성·네임스페이스와 스키마 검증 | 문서 중심 시스템, 기존 기업 시스템과의 호환 | 장황함과 큰 문서의 메모리 사용 |
| CSV | 행과 열을 평문으로 표현 | 스프레드시트, 표 데이터 내보내기 | 쉼표·따옴표·줄바꿈·인코딩·빈 값과 자료형 해석 |
| YAML | 들여쓰기 기반, 주석과 여러 줄 텍스트 지원 | 사람이 편집하는 설정 | 공백과 특수문자, 파서의 값 해석 |

책은 API에는 JSON, 설정에는 YAML, 다운로드에는 CSV처럼 목적별로 조합하는 접근을 설명한다.

CSV에서는 빈 필드와 따옴표를 포함한 값 등을 단순한 문자열 분리로 처리하기 어렵다. 형식에 맞는 파서와 옵션을 사용한다. YAML도 운영에 적용하기 전에 구조와 값이 의도대로 해석되는지 검증한다.

## 5. 특수한 데이터에서 확인할 것

### 이진 데이터

이미지, 문서, 오디오처럼 바이트로 다루는 콘텐츠에는 형식에 맞는 라이브러리를 사용한다. 텍스트 형식에 포함할 때는 Base64 같은 표현을 사용할 수 있다.

큰 파일을 모두 메모리에 올리는 비용과 손상·불완전한 파일 처리도 고려한다. 저장과 전달, 표시의 경계를 구분하면 어디에서 변환이 필요한지 명확해진다.

### 날짜와 시간

시간대, 일광절약 시간제, 형식 변환 때문에 날짜와 시간은 문자열 처리 이상의 문제다.

책은 시점을 UTC로 저장하고 표시 단계에서 현지 시간대로 변환하는 방식, 시스템 간 ISO 8601 사용과 검증된 날짜 라이브러리 활용을 권한다.

이 지침은 같은 시점을 여러 지역에서 표현할 때 유용하다. 생일처럼 시간대 변환이 필요 없는 날짜와 특정 시점은 의미가 다르므로 어떤 값을 저장하는지 먼저 구분한다. 화면에서도 시간대가 중요한 정보라면 이를 명시한다.

### 대규모 데이터와 동시 접근

전체 CSV를 읽어 올리기보다 레코드를 순차 처리하는 스트리밍, API 결과의 페이지 처리와 필요한 열만 조회하는 방법을 고려한다.

동시 접근에서는 잠금, 원자적 연산이나 불변 자료구조 등으로 경쟁을 관리한다. 작은 개발 데이터만으로 판단하지 말고 운영과 비슷한 규모에서 메모리와 처리 시간을 확인한다.

## 6. 저장소는 접근 패턴과 요구사항에 맞춰 선택

책이 제시하는 주요 기준은 데이터 관계의 복잡성, 읽기·쓰기 비중, 질의 형태, 성장 규모와 일관성 요구다.

| 유형 | 주된 모델과 접근 | 적합한 문제 |
| --- | --- | --- |
| 관계형 | 테이블, 키와 관계, SQL | 명확한 관계와 복잡한 조회, 트랜잭션 |
| 문서형 | 유연한 문서와 중첩 구조 | 레코드별 속성이 다른 카탈로그와 콘텐츠 |
| 키-값 | 키로 값을 찾는 단순한 접근 | 세션, 설정과 캐시 |
| 그래프 | 노드와 관계를 탐색 | 연결과 경로가 중요한 추천·네트워크 |
| 벡터 | 임베딩의 유사도 검색 | 의미 검색, 유사 콘텐츠 검색과 RAG |

책은 사용자·게시물·태그·댓글의 관계가 명확한 블로그와, 상품마다 속성이 달라지는 카탈로그를 비교한다. 중요한 것은 유행하는 기술을 선택하는 것이 아니라 현재의 데이터를 어떻게 읽고 갱신할지 설명할 수 있는 선택이다.

벡터 검색의 유사성은 모델과 표현에 따른 판단이다. 가까운 벡터라는 결과를 정확한 사실 일치나 사업적으로 정답인 추천과 동일하게 해석하지 않는다.

처음부터 모든 종류의 저장소를 도입하지 않는다. 필요에 따라 발전할 여지를 남기되 운영해야 할 기술의 수와 복잡성도 비용이다.

## 7. ACID와 트랜잭션의 책임

| 속성 | 의미 |
| --- | --- |
| Atomicity | 묶인 작업을 모두 반영하거나 반영하지 않음 |
| Consistency | 정의된 제약과 무결성 규칙을 유지함 |
| Isolation | 동시 작업 사이의 간섭을 격리 수준에 따라 제어함 |
| Durability | 커밋된 결과를 장애 이후에도 유지하도록 보장함 |

책의 송금 예시에서는 한 계좌에서 출금하고 다른 계좌에 입금하는 두 작업을 같은 트랜잭션에 둔다. 한쪽만 성공하면 전체를 되돌려 부분적인 반영을 막는다.

관련 작업의 경계를 정의하는 것은 개발자의 책임이다. 트랜잭션을 지원하는 데이터베이스를 선택했다는 사실만으로 분리된 작업이 자동으로 하나의 원자적 작업이 되지는 않는다.

또한 데이터베이스의 제약을 지켰다고 모든 사업 규칙을 검증한 것은 아니다. 동시성 문제를 얼마나 막는지도 실제 격리 수준과 사용 방식에 따라 확인해야 한다.

## 8. 영속성 추상화의 수준

| 방식 | 장점 | 부담 |
| --- | --- | --- |
| 직접 SQL·드라이버 접근 | 질의와 데이터 접근을 세밀하게 제어 | 매핑, 자원과 오류 처리 코드가 필요 |
| Repository 패턴 | 도메인과 데이터 접근의 책임 분리 | 인터페이스와 구현을 유지해야 함 |
| ORM | 객체와 관계형 저장의 매핑을 지원 | 생성 질의와 로딩 동작이 숨겨질 수 있음 |

Repository와 ORM은 반드시 대립하는 선택이 아니다. Repository 구현에 SQL이나 ORM을 사용할 수 있다.

추상화가 높을수록 항상 좋은 것은 아니다. 팀의 SQL·ORM 경험, 일정, 디버깅 난이도와 성능 요구를 함께 본다. 사용하는 추상화 아래에서 어떤 질의가 실행되는지 이해해야 한다.

책은 일반 작업에는 ORM을 활용하고 성능이 중요한 경로에서는 직접 SQL을 검토하는 혼합 접근도 제시한다.

## 9. 연결 풀과 자원 관리

연결 풀은 매 작업마다 데이터베이스 연결을 새로 만드는 대신 기존 연결을 재사용한다. 연결 생성 비용을 줄이고 동시에 사용할 자원을 관리하는 수단이다.

풀 크기를 크게 하면 무조건 빨라지는 것은 아니다. 데이터베이스가 감당할 수 있는 동시 작업과 애플리케이션의 요구를 함께 봐야 한다.

연결을 얻은 뒤 반납하지 않거나 긴 트랜잭션이 오래 점유하면 다른 요청이 대기할 수 있다. 책은 활성·유휴·대기 연결과 최대 크기를 관찰해 병목과 낭비를 구분하도록 설명한다.

## 10. 일관성 모델: 변경이 언제 보이는가

ACID의 일관성은 데이터가 규칙을 지키는지에 관한 것이다. 분산 시스템의 일관성 모델은 변경과 읽기가 어떤 순서와 범위로 관찰되는지에 관한 것이다. 두 의미를 구분해서 읽는다.

| 모델 | 중심 개념 | 고려할 상황 |
| --- | --- | --- |
| 강한 일관성 | 완료된 변경을 이후 읽기에서 일관되게 관찰 | 오래된 상태에 따른 잘못된 판단이 치명적일 때 |
| 최종 일관성 | 일시적 차이를 허용하되 변경이 수렴 | 일정한 반영 지연을 감수할 수 있을 때 |
| 인과 일관성 | 인과관계가 있는 변경의 순서를 유지 | 관련 편집과 반응의 순서가 중요할 때 |
| 세션 일관성 | 한 사용자 세션에 일관된 관찰을 제공 | 자신의 변경을 다시 확인하는 경험이 중요할 때 |

책은 잔액·재고, 활동 로그·피드, 장바구니·초안처럼 오래된 데이터가 미치는 영향이 다른 사례를 비교한다. 같은 시스템에서도 데이터의 성격에 따라 요구가 달라질 수 있다.

특정 제품명만으로 보장을 단정하기보다 읽기 경로, 복제와 실제 설정을 확인해야 한다.

### CAP가 설명하는 선택

책은 분산 시스템에서 일관성(C), 가용성(A), 네트워크 분할에 대한 대응(P)의 득실을 설명한다.

네트워크가 끊어져 서버끼리 소통하지 못할 때, 최신 상태를 보장하기 위해 요청을 제한할지, 일부 오래된 응답을 허용하면서 요청 처리를 계속할지가 핵심 선택이다.

금융과 피드는 오래된 상태를 허용하는 비용이 다르다. 모든 데이터에 동일한 선택을 적용하기보다 사업적 영향과 실패 조건을 구체화한다.

## 11. 캐시 전략과 일관성

캐시는 자주 읽는 데이터를 더 빠른 저장소에 두어 원본 조회의 부하와 지연을 줄인다. 동시에 원본과 다른 상태가 될 수 있는 복사본을 추가한다.

| 전략 | 동작 | 장점 | 확인할 위험 |
| --- | --- | --- | --- |
| Cache-aside | 캐시 miss 때 원본을 조회해 적재 | 필요한 데이터부터 캐시하며 읽기에 유리 | 첫 조회 비용, 무효화와 오래된 값 |
| Write-through | 쓰기 경로에서 원본과 캐시를 갱신 | 갱신 직후 읽기 상태를 맞추기 쉬움 | 쓰기 비용과 한쪽만 성공하는 실패 |
| Write-back | 캐시에 먼저 쓰고 원본에 비동기 반영 | 쓰기 응답을 빠르게 할 수 있음 | 원본 반영 전 유실과 불일치 |

책은 TTL로 일정 시간 뒤 만료시키는 방법과 쓰기 전략을 일관성 요구에 맞춰 선택하도록 설명한다.

원본과 캐시를 한 메서드에서 차례로 갱신하는 것만으로 두 저장소가 원자적으로 변경되는 것은 아니다. 중간 실패와 재시도 시 어떻게 복구할지까지 정의해야 한다.

### 캐시를 도입하기 전에

- 데이터가 얼마나 자주 바뀌는가?
- 오래된 값을 보여주면 어떤 피해가 생기는가?
- 현재 원본 조회가 얼마나 비싼가?
- 측정한 병목이 있는가?

책은 자주 바뀌지 않는 상품 정보와 초 단위로 가격이 바뀌는 거래 플랫폼을 비교한다. 같은 캐시 만료 시간이라도 사용자에게 미치는 위험은 다르다.

캐시는 실패 지점, 메모리 사용과 무효화의 책임을 추가한다. 측정한 이점이 증가하는 복잡성을 정당화하는지 판단한다.

## 12. 데이터 증가에 대응하기

| 방법 | 목적 | 부담 |
| --- | --- | --- |
| 수직 확장 | 한 서버의 CPU·메모리 증가 | 자원 한계와 비용 |
| 읽기 복제본 | 읽기 부하를 분산 | 복제 지연과 읽기 경로의 선택 |
| 수평 확장 | 여러 서버로 처리와 데이터를 분산 | 운영과 일관성 관리 |
| Sharding | 키를 기준으로 데이터를 나눠 보관 | 분할 키, 교차 조회와 재분배 |

캐시는 선택한 데이터의 임시 복사본이고 읽기 복제본은 데이터베이스 복제의 결과다. 어느 쪽도 지연과 상태 차이를 생각하지 않고 사용할 수는 없다.

질의 지연, CPU, 메모리, 데이터 증가와 사용자 불만을 정기적으로 살핀다. 오래된 데이터의 보존·아카이빙, 인덱스 점검과 질의 개선도 성장 대응의 일부다.

## 13. 효율적인 질의: 필요한 데이터만 가져오기

책은 `SELECT *`로 활성 사용자 전체를 읽는 예시를 필요한 열과 제한된 결과만 읽는 방식으로 개선한다.

필요하지 않은 열과 행을 가져오면 데이터베이스의 읽기뿐 아니라 네트워크 전송, 객체 생성과 메모리 비용도 늘어난다.

필요한 정보를 명시하는 것은 성능과 함께 코드가 요구하는 데이터 계약을 드러내는 효과도 있다. 다만 결과를 제한할 때는 기능이 요구하는 데이터가 누락되지 않도록 페이지 처리와 정렬을 함께 설계한다.

### Prepared statement

SQL 문자열에 입력값을 직접 이어 붙이지 않고 매개변수로 전달한다. 값과 질의 구조를 분리해 주입 공격을 예방하고 질의 재사용을 지원하는 방법이다.

책은 성능상의 이점도 설명하지만 계획 재사용과 개선 폭은 데이터베이스와 드라이버, 설정에 따라 확인해야 한다. 특정 향상률을 모든 환경에 적용하지 않는다.

## 14. 인덱스는 읽기 비용을 줄이는 대신 쓰기 비용을 추가한다

인덱스는 조건에 맞는 데이터를 찾는 경로를 제공한다. WHERE, JOIN, ORDER BY와 GROUP BY에서 자주 쓰는 열과 복합 조건을 검토한다.

인덱스가 늘면 저장 공간과 갱신 비용도 늘어난다. 데이터 분포, 조회 비중과 쓰기 빈도를 고려해 선택한다.

책은 고윳값이 적은 열을 주의 대상으로 제시한다. 이를 모든 저기수 열에 인덱스가 무의미하다는 절대 규칙으로 보기보다, 조건이 데이터를 얼마나 좁히는지와 실제 실행 계획을 확인하는 기준으로 삼는다.

## 15. 페이지 처리에도 비용이 있다

LIMIT·OFFSET은 간단하지만 깊은 페이지에서 앞선 행을 읽고 건너뛰는 비용이 커질 수 있다. 전체 개수를 세는 COUNT 질의도 별도 비용이다.

책은 마지막으로 본 키 이후의 데이터를 가져오는 방식, 전체 개수 캐시·추정, 무한 스크롤을 대안으로 제시한다.

Keyset 방식은 정렬 기준과 다음 페이지의 경계를 일치시켜야 한다. 숫자 페이지 이동이 필요한지, 전체 건수가 꼭 필요한지 같은 UI 요구도 함께 검토한다.

## 16. 실행 계획과 관측으로 병목 찾기

옵티마이저는 사용 가능한 인덱스와 통계 등을 바탕으로 SQL을 실행할 방법을 선택한다. EXPLAIN은 계획을 보여주고 EXPLAIN ANALYZE는 실제 실행의 관찰값을 함께 제공한다.

- 테이블 접근 순서와 조인 방식
- 전체 탐색과 인덱스 사용 여부
- 예상 행 수와 실제 행 수의 차이
- 각 단계의 비용과 실행 시간

전체 탐색이 있다는 사실만으로 잘못된 계획이라고 단정하지 않는다. 읽을 데이터의 비율과 규모에 따라 합리적일 수 있다.

개발과 운영의 데이터 분포, 인덱스와 통계가 다르면 동일한 SQL도 다른 계획으로 실행될 수 있다. 환경별 차이도 확인한다. 실제 실행을 수반하는 분석은 대상 작업과 환경의 영향을 고려한다.

### 로그·지표·추적의 역할

| 자료 | 확인할 내용 |
| --- | --- |
| 로그 | 오류, 제약 위반과 주요 이벤트 |
| 지표 | 연결 풀 상태, 질의·트랜잭션 시간과 오류율 |
| 추적 | 한 요청의 구성요소별 지연과 데이터베이스 호출 횟수 |

책은 요청 시간 대부분이 한 질의에서 소비되는 경우와, 빠른 질의가 수십 번 이어지는 N+1 문제를 구분한다. 한 질의의 속도만 보지 말고 전체 요청에서 호출이 어떻게 누적되는지 확인해야 한다.

## 17. 가독성과 성능의 균형

책의 주문 조회 사례는 ORM으로 목록을 읽은 뒤 애플리케이션에서 금액을 필터링하는 방식과, 필요한 조건을 SQL에 넣어 결과만 읽는 방식을 비교한다.

판단 기준은 데이터 규모, 응답 요구, 유지보수 비용, 팀의 SQL 경험과 향후 변화다. 측정한 병목 없이 모든 코드를 저수준 질의로 바꾸거나, 추상화가 편하다는 이유로 비효율을 방치하지 않는다.

## 18. 데이터 이전은 복사보다 넓은 작업이다

| 방식 | 특징 | 관리할 부분 |
| --- | --- | --- |
| 일괄 이전 | 전체를 한 번에 전환 | 점검 시간과 전체 실패의 영향 |
| 점진적 이전 | 일부를 옮겨 검증하고 범위를 확대 | 구·신 시스템의 공존과 동기화 |

책은 직원 데이터를 부서별로 나누어 이전하는 예를 들며 영향이 작은 그룹에서 먼저 경험과 검증을 확보하는 방식을 설명한다.

선택은 데이터 규모, 허용 중단 시간, 복잡성과 위험에 따라 달라진다. 묶음 처리 크기도 고정값으로 확정하기보다 PoC로 메모리와 처리 능력을 확인한다.

### ETL

1. Extract: 원천 데이터를 추출한다.
2. Transform: 대상 형식과 규칙에 맞춰 변환한다.
3. Load: 대상 저장소에 적재한다.

추출은 원본 시스템 부하와 속도 제한, 변환은 누락·잘못된 형식, 적재는 제약 위반을 고려해야 한다. 실패한 레코드와 단계, 이유를 남겨 검증과 재처리를 가능하게 한다.

### 공존 기간의 동기화

메시지 큐와 CDC로 변경을 전달하고 reconciliation으로 차이를 찾아 조정할 수 있다. 두 시스템에 쓰는 방식에서도 한쪽의 실패와 재시도, 중복 처리를 검토해야 한다.

## 19. 스키마와 데이터 변환도 버전 관리

코드와 마찬가지로 스키마 변경도 이력과 적용 순서를 추적해야 한다. 책은 Flyway 등의 도구가 이력 테이블과 버전별 스크립트를 비교해 아직 적용하지 않은 변경을 실행하는 원리를 설명한다.

새 열을 추가하는 것만으로 변환이 끝나지 않을 수 있다. 기존 주소 문자열을 거리, 도시, 우편번호 등으로 나누는 사례처럼 저장된 값도 새 구조에 맞게 옮겨야 한다.

- 스키마 변경과 관련된 데이터 변환을 함께 추적한다.
- 가능하면 공존할 애플리케이션 버전과 호환되게 변경한다.
- 재실행 시 중복이나 손상이 없도록 설계한다.
- 작은 샘플로 변환 결과를 확인한 뒤 확대한다.
- 실패와 원상복구 계획을 준비한다.

도구가 적용 이력을 관리하는 것과 작업 자체가 멱등적인 것은 다르다. 또한 DDL과 데이터 변경의 원자성은 데이터베이스와 작업의 트랜잭션 지원을 확인해야 한다. 버전을 관리한다고 자동으로 모든 변경이 함께 롤백되는 것은 아니다.

## 실천

1. 기능 하나의 데이터 구조, 읽기·쓰기 경로와 일관성 요구를 정리한다.
2. 운영 규모에 가까운 조건에서 질의 시간과 호출 수를 관찰한다.
3. 필요한 열과 행, 인덱스와 페이지 처리부터 개선 후보를 찾는다.
4. 캐시 도입 전 오래된 데이터의 허용 범위와 실패 처리 방식을 정의한다.
5. 데이터 형식 변환에서 빈 값과 특수문자, 날짜 의미를 검증한다.
6. 작은 데이터 이전을 실행하며 건수, 값과 관계가 보존되는지 확인한다.

2. 같은 화면에서 즉시 일치해야 하는 데이터와 늦게 반영되어도 되는 데이터는 무엇일까?
3. 응답이 느릴 때 캐시와 인덱스, 질의 개선 중 어떤 근거로 우선순위를 정할까?
