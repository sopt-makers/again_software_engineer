### 내가 생각하는 핵심 문장 정리

6장은 새로운 프로젝트나 익숙하지 않은 코드베이스에 합류했을 때, **처음부터 모든 코드를 이해하려고 하기보다 프로젝트의 목적과 맥락을 먼저 파악하고 점진적으로 이해의 범위를 넓혀가는 방법**에 대해 다루는 내용이었습니다.

- 코드를 파악하기 전에 먼저 **프로젝트가 왜 존재하는지, 누구를 위한 것인지, 회사나 사업에서 어떤 의미를 가지는지 이해해야 한다.**

- 프로젝트의 문서와 공개된 정보를 충분히 살펴보되, **문서에서 얻은 내용은 반드시 실제 코드와 대조하며 확인해야 한다.** 문서는 오래되거나 잘못될 수 있지만 실제 동작은 코드에 남아 있기 때문이다.

- 프로젝트를 이해할 때는 모든 것을 한꺼번에 파악하려 하기보다 **프로젝트 구조 → 실행 흐름 → API 요청 → 외부 의존 관계 → 내부 프레임워크와 라이브러리처럼 작은 단위로 나누어 접근해야 한다.**

- 모르는 것을 질문하는 것을 두려워하지 않아야 한다. **멍청한 질문이란 없으며, 오히려 질문하지 않는 것이 시스템을 제대로 이해할 기회를 놓치는 일이 될 수 있다.**

- 기존 코드를 리팩터링하기 전에는 테스트를 추가하고, 먼저 **현재 동작을 명확하게 기록하고 보호한 뒤 변경하는 것이 안전하다.**

- 코드를 발견했을 때보다 조금 더 좋은 상태로 남겨두는 **스카우트 규칙을 따르되, 발견한 모든 문제를 즉시 고치려고 할 필요는 없다.**

- 기존 시스템을 개선할 때는 한 번에 큰 변화를 만들기보다 **쉽게 되돌릴 수 있는 작은 변경을 점진적으로 진행하는 것이 더 안전하다.**

- 코드를 파악하기 전에 먼저 프로젝트의 목적과 의도를 이해해야 한다. 이 코드가 존재하는 전반적인 이유는 무엇인가? 이해관계자는 누구인가? 회사에서 이 프로젝트는 어떤 의미인가? 사업에서 큰 비중을 차지하는가?
- 멍청한 질문이란 없다. 질문하지 않는 것만이 멍청한 일이다.
- 프로젝트에 대한 공개 정보를 찾아보자. 고객의 관점에서 바라보려 노력해야 한다.
- 사용자 페르소나는 사용자 유형과 목표와 고충을 이해하는 데 도움이 되며, 어떤 기술적 결정이 내려진 가치 있는 맥락을 알려준다.
- 아키텍처 결정 기록을 포함해 읽을 수 있는 모든 문서를 샅샅이 살펴보자.
- 문서는 거짓말을 할 수 있지만 코드는 절대 거짓말을 하지 않는다. 읽은 내용을 실제 코드와 대조하며 확인하자.
- 프로젝트를 이해할 때는 프로젝트 구조 이해 → 실행 흐름 파악 → API 요청 추적 → 외부 의존 관계 파악 → 내부 프레임워크와 라이브러리 파악의 흐름으로 접근할 수 있다.
- 실행 흐름을 파악할 때 처음부터 깊게 분석하기보다 진입점을 찾고 코드가 어떤 방향으로 흐르는지 이해하는 데 집중하자.
- 모든 것을 한꺼번에 이해하려고 하는 것은 지나치게 부담스럽고 비효율적이다. 대신 복잡한 시스템을 다루기 좋은 조각으로 나누는 데 집중해야 한다.
- 리팩터링 전에 테스트를 추가하라. 이에 대한 첫 번째 목표는 동작 변경이 아니라 기존 동작의 문서화이다.
- 스카우트 규칙을 따르자. 코드를 처음 발견했을 때보다 항상 더 좋게 남겨두자.
- 개선할 수 있는 코드를 모두 즉각 개선해야 하는 것은 아니다.
- 쉽게 되돌릴 수 있는 변경을 점진적으로 진행하는 것이 전체 시스템에 영향을 주지 않고 기존 코드를 수정하는 가장 안전한 방법이다.

### 이야기해보면 좋을 내용

메이커스처럼 이미 운영되고 있는 프로젝트에 새롭게 합류했을 때, **우리는 실제로 어떤 순서와 방법으로 기존 코드베이스를 이해하고 있는지** 이야기해보면 좋을 것 같다고 생각했어요.

그리고 새로운 사람이 메이커스에 합류한다고 했을 때, **프로젝트 구조나 주요 실행 흐름, API 구조, 내부에서 사용하는 라이브러리와 함께 어떤 문서나 맥락을 먼저 전달해주면 빠르게 프로젝트에 익숙해질 수 있을지** 이야기해보면 좋을 것 같습니다.
