# 6장. 낯선 시스템에 빨리 친숙해지기

## 핵심 요약

- 낯선 시스템은 제품의 목적과 사용자를 이해하는 데서 출발하고, 구조와 실행 흐름을 연결해 파악한다.
- 문서, 설정, 코드와 실제 실행을 대조하며 외부 의존성과 내부 프레임워크까지 확인한다.
- 전체 시스템을 한꺼번에 이해하려 하지 않고 업무 흐름 하나부터 정신 모델을 점진적으로 확장한다.
- 리팩터링 전에 기존 동작을 테스트로 확인하고, 작은 변경마다 그 동작이 유지되는지 검증한다.
- 스카우트 규칙은 당면한 과제와 균형을 맞춰 적용하고, 되돌릴 수 있는 커밋과 PR로 위험을 관리한다.

## 1. 기존 시스템을 다루는 것도 핵심 역량이다

기존 코드에는 이전 결정과 기술 부채가 있지만, 이미 갖춰진 인프라와 구조 덕분에 당면한 문제에 집중할 수 있다는 장점도 있다.

낯선 시스템에서 불안한 것은 코드뿐 아니라 언어, 도구와 도메인도 익숙하지 않기 때문이다. 명확한 탐색 절차를 갖추면 알아야 할 범위를 좁히고 기여할 출발점을 찾을 수 있다.

처음부터 모든 것을 아는 것이 목표는 아니다. 오랫동안 일한 팀원도 시스템 전체를 완전히 이해하지 못할 수 있다.

## 2. 제품의 큰 그림부터 이해하기

세부 구현이나 프레임워크 버전에 집중하기 전에 다음 질문에 답한다.

- 이 제품이 존재하는 이유는 무엇인가?
- 고객과 주요 이해관계자는 누구인가?
- 어떤 업무와 사업적 가치를 지원하는가?
- 사용자는 어떤 목표와 불편을 가지고 있는가?

제품 관리자나 제품 책임자는 목적과 사용자 맥락을 설명해 줄 수 있다. 기술 리더, 아키텍트와 초기 개발자는 설계의 이유와 제약을 이해하는 데 도움을 준다.

사용자 페르소나와 공개 자료도 기술적 선택의 맥락을 파악하는 단서다. 대화에서 배운 용어와 아직 모르는 부분을 메모해 이후 탐색의 기준으로 삼는다.

## 3. 문서를 읽되 실행되는 코드와 대조하기

README, 온보딩 문서, ADR을 읽어 빌드와 실행 방법, 아키텍처, 과거의 결정을 파악한다.

책에서는 저자가 인증 문서를 사흘 동안 읽었지만 실제로는 두 버전 전 문서였던 사례를 소개한다. 짧은 동료와의 대화로 문서가 현재 시스템과 다르다는 사실을 알게 되었다.

문서는 이해를 돕는 출발점이다. 문서의 설명이 현재 코드와 실행 결과에 부합하는지 확인해야 한다. 실행되는 코드는 현재 동작을 보여주지만 그것이 요구사항에도 맞다는 뜻은 아니다.

실행 방법의 누락이나 오래된 설명을 발견하면 기록하고 보완한다. 온보딩 과정에서 찾은 작은 빈틈도 다음 구성원에게 도움이 되는 기여다.

## 4. 아키텍처와 프로젝트 구조 파악하기

폴더 배치는 코드 탐색의 지도지만 실제 의존 관계까지 모두 설명하지는 않는다. 구조에서 얻은 가설을 호출 관계와 구현으로 확인한다.

| 구성 방식 | 탐색할 단서 | 이해할 내용 |
| --- | --- | --- |
| 계층별 패키지 | controllers, services, repositories 등 | 기술적 책임과 계층 사이의 호출 관계 |
| 기능별 패키지 | users, products, orders 등 | 한 기능을 구현하는 코드의 응집과 흐름 |
| 헥사고날 아키텍처 | domain, ports, adapters 등 | 핵심 규칙과 외부 기술의 경계 |
| 마이크로서비스 | 독립 서비스와 gateway, 공통 모듈 | 서비스 내부뿐 아니라 전체 생태계의 연결 |

책은 어느 방식을 선택하라는 처방보다 현재 프로젝트가 어떤 구조인지 알아보는 방법을 설명한다. 혼합된 구조라면 기능마다 경계가 어떻게 다른지 확인한다.

## 5. 진입점을 찾고 요청의 여정 추적하기

진입점은 시스템이 외부 자극을 받아 작업을 시작하는 장소다.

- main·부트스트랩 코드
- 공개 API와 웹 UI
- 이벤트 핸들러와 메시지 소비자
- 예약 작업과 배치
- 생성·시작·종료 수명 주기 훅
- 명령행 처리와 확장 인터페이스
- 데이터베이스 트리거와 저장 프로시저

하나의 진입점을 선택하고 입력이 어디에서 검증되고 변환되며 저장되는지 따라간다. 응답과 오류가 어떤 경로로 돌아오는지도 확인한다.

### 책의 사례: 반려동물 추가

Spring PetClinic에서 사용자가 반려동물 추가 양식을 제출하면 요청 처리 메서드로 들어간다. 중복 이름과 미래의 생일 같은 조건을 검사하고, 오류가 있으면 양식을 다시 보여준다. 정상 입력은 소유자에 반려동물을 추가하고 저장한 뒤 소유자 화면으로 이동시킨다.

단순히 컨트롤러의 코드를 읽는 것보다 화면의 입력, 요청 데이터, 검증 조건, 저장과 응답을 연결하면 기능의 전체 의미를 이해하기 쉽다.

## 6. 관찰 도구마다 얻는 정보 구분하기

| 도구 | 확인할 정보 |
| --- | --- |
| 브라우저 Network | 실제 요청 URL, 메서드, 헤더, 본문, 상태 코드와 응답 |
| API 테스트 도구 | UI를 거치지 않은 입력·인증·응답 계약 |
| 로그 | 주요 이벤트, 오류와 요청의 진행 기록 |
| 디버거 | 변수의 실제 값, 객체 상태와 조건문의 평가 결과 |

API를 직접 호출하면 누락된 필드, 잘못된 타입, 빈 문자열, null, 승인되지 않은 요청을 다르게 처리하는지 확인할 수 있다.

로그는 실행의 단서를 제공하지만 남겨진 내용 밖의 상태는 보여주지 못한다. 디버거는 복합 조건을 하나씩 확인해 왜 특정 분기로 들어갔는지 이해하는 데 유용하다.

책의 중복 이름 검사 사례에서는 이름이 비어 있지 않은지, 새 객체인지, 같은 이름의 반려동물이 존재하는지 각각의 평가 결과를 확인한다. 예상과 다른 분기는 추측보다 실제 값으로 설명해야 한다.

## 7. 외부 의존 관계와 내부 프레임워크 파악하기

### 외부 의존성

애플리케이션은 데이터베이스, 캐시, 결제·이메일 서비스, 메시지 브로커 등에 연결될 수 있다.

설정 파일의 접속 정보와 endpoint, Docker Compose의 서비스, Kubernetes의 배포 구성을 살펴 의존성을 찾는다. 코드의 호출 위치와 연결하면 기능별로 어느 의존성이 필요한지 이해할 수 있다.

### 내부 프레임워크

사내 기반 클래스, 자체 어노테이션, 범용 유틸리티와 독자적인 설정은 표준 프레임워크만 알아서는 이해하기 어려운 동작을 추가할 수 있다.

책이 제시하는 징후는 다음과 같다.

- 회사 이름이나 framework·internal 계열 패키지
- BaseService, AbstractController 같은 자체 기반 클래스
- 표준 프레임워크에 없는 어노테이션
- 여러 책임을 처리하는 광범위한 유틸리티
- 자체 규칙으로 구성된 방대한 설정

먼저 실제 사용 사례와 테스트를 읽고, 변경 이력과 동료에게서 도입 이유를 확인한다. 특별한 성능·보안 요구나 당시 외부 도구의 한계 때문이었을 수 있다.

표준 도구로 바꿀 수 있어 보여도 현재 사용처와 계약, 유지보수 비용을 비교한 뒤 판단한다. 사용하는 과정에서 배운 내용을 기록하고 점진적으로 개선한다.

## 8. 정신 모델을 점진적으로 구축하기

정신 모델은 시스템이 어떻게 동작하는지 설명할 수 있는 머릿속의 구조다. 결제, 가입, 후기 등록처럼 업무 흐름 하나부터 구축하면 인지 부담을 줄일 수 있다.

책은 다음 순서로 범위를 넓힌다.

1. 단일 메서드의 동작을 이해한다.
2. 해당 클래스와 직접 의존성을 확인한다.
3. 여러 구성요소를 통과하는 기능 흐름을 연결한다.
4. 보안과 트랜잭션 같은 횡단 관심사를 확인한다.

### 목적에 맞는 시각화

| 표현 | 확인할 내용 |
| --- | --- |
| 순서도 | 절차와 분기 |
| 순차 다이어그램 | 시간에 따른 호출과 응답 |
| 컴포넌트 다이어그램 | 구성요소와 의존 관계 |
| ERD | 데이터 구조와 관계 |
| 마인드 맵 | 개념과 학습 범위 |

책의 결제 예시는 장바구니 확인, 결제 처리, 주문 확정이라는 큰 흐름에서 시작한다. 이해가 깊어지면 UI, API, 서비스, 데이터베이스와 결제 대행사 사이의 호출까지 확장한다.

그림의 완성도보다 현재 이해를 드러내고 틀린 가정을 확인하는 것이 중요하다. AI가 만든 다이어그램 초안도 실제 코드와 대조하고 팀원에게 검증받는다.

## 9. 반복 가능한 탐색 절차

책의 샘플 프로세스는 다음과 같이 묶을 수 있다.

1. 저장소를 받아 README, 코딩 표준과 아키텍처 자료를 읽는다.
2. 빌드 스크립트, 의존성, 프로젝트 구조와 CI/CD를 확인한다.
3. 필요한 런타임과 도구, 데이터 저장소를 준비한다.
4. IDE에서 애플리케이션과 테스트를 실행하고 중단점으로 추적한다.
5. 명령행에서도 빌드·테스트·실행 절차를 확인한다.
6. 명령, 용어, 아키텍처와 질문을 기록하고 공유한다.

기능과 버그를 맡을 때마다 이 과정을 반복하며 시스템의 다른 부분을 연결한다.

## 10. 안전한 리팩터링: 동작을 먼저 고정하기

리팩터링은 관찰 가능한 동작을 유지하면서 구조를 개선하는 작업이다. 기존 테스트를 먼저 실행해 기준 상태를 확인한다.

관련 테스트가 없다면 다음 순서로 진행한다.

1. 현재 동작을 표현하는 테스트를 작성한다.
2. 기존 구현이 통과하는지 확인한다.
3. 작은 구조 변경을 수행한다.
4. 같은 기대 동작이 유지되는지 확인한다.

현재 동작을 기록하는 테스트가 그 동작이 사업적으로 옳다는 증거는 아니다. 기존 동작 보존과 버그 수정의 기대 결과를 구분해야 한다.

### 책의 사례: 주문 합계

합계 계산에서 소계와 할인 적용을 별도 함수로 분리한다. 상품 가격 10에 수량 2, 가격 15에 수량 1이면 소계는 35이고, 10% 할인을 적용하면 31.5다.

리팩터링 전후 이 결과가 같아야 한다. 구조를 개선하는 과정에서 기대 결과를 바꿔 통과시키면 보존하려던 동작이 달라졌는지 알 수 없게 된다.

## 11. 스카우트 규칙과 범위의 균형

스카우트 규칙은 작업한 코드를 처음 발견했을 때보다 더 나은 상태로 남기자는 원칙이다. 이름 개선, 문서 보완, 복잡한 메서드 분리, 죽은 코드 제거 등이 작은 개선의 후보다.

| 개선을 고려할 때 | 미루는 편이 나을 때 |
| --- | --- |
| 현재 작업의 이해와 변경을 방해함 | 잘 동작하고 변경할 일이 거의 없음 |
| 기능 추가나 버그 수정과 직접 연결됨 | 작업 범위를 크게 넘어서는 변경이 필요함 |
| 여러 사람이 자주 수정하는 영역임 | 검증 수단이 부족하거나 위험이 이득보다 큼 |
| 성능 문제의 원인으로 확인됨 | 마감 압박 속에서 충분한 검증이 어려움 |

주변 코드를 모두 정리하다 원래 문제를 해결하지 못하는 상황을 경계한다. 작은 개선도 목적과 영향 범위를 설명할 수 있어야 한다.

## 12. 작고 되돌릴 수 있는 변경

책의 주문 처리 예시는 유효성 검사, 합계, 할인, 배송비, 세금, 결제, 재고와 알림을 포함한다. 전체를 한 번에 바꾸기보다 한 책임씩 분리하고 각 단계에서 검증한다.

변경 관리에는 네 가지가 필요하다.

- 가시성: 무엇을 왜 바꾸었는지 설명한다.
- 검증: 테스트, 리뷰와 정적 분석으로 결과를 확인한다.
- 복구: 문제가 생기면 어떻게 되돌릴지 준비한다.
- 관찰: 적용 후 오류와 성능, 예상 밖의 영향을 확인한다.

작은 변경은 테스트와 리뷰를 집중시키고, 문제가 생긴 위치를 좁히며, 되돌리는 부담을 줄인다.

## 13. 버전 관리와 PR

커밋은 독립적이고 논리적으로 하나의 변경을 담아야 한다. 메시지에는 무엇뿐 아니라 어떤 문제를 왜 해결했는지도 남긴다.

책은 단순한 ‘버그 수정’ 대신 할인 코드가 두 번 적용되는 조건과 주문당 한 번만 적용하도록 바꾼 이유를 설명하는 메시지를 예로 든다.

브랜치 수명을 짧게 유지하면 main과 멀어져 통합이 어려워지는 일을 줄일 수 있다. 최신 변경을 반영하는 과정에서도 공유된 이력을 다시 쓰는 작업은 주의해야 한다.

PR은 작은 문제에 집중하고 요구사항, 변경 이유와 검증 결과를 전달한다. 리뷰는 작성자를 평가하기보다 해결책을 개선하는 과정이다.

## 실천

1. 낯선 프로젝트에서 제품 목적, 실행 방법과 주요 의존성을 기록한다.
2. 사용자 행동 하나를 UI부터 API와 저장 결과까지 추적한다.
3. 실제 흐름의 그림을 만들고 동료에게 확인받는다.
4. 이해하기 어려운 함수의 현재 동작을 테스트로 고정한다.
5. 작은 리팩터링 하나를 수행하고 원래 동작이 유지되는지 검증한다.
6. 변경 이유, 영향 범위와 복구 방법을 PR에 설명한다.

## 토론 질문

1. 낯선 시스템에서 첫 기여를 하기 전에 어느 정도까지 이해해야 할까?
2. 문서와 코드, 사용자가 기대하는 동작이 다를 때 무엇부터 확인할까?
3. 스카우트 규칙을 적용하면서 작업 범위가 커지는 것을 어떻게 막을까?
4. 현재 동작을 보존하는 리팩터링과 잘못된 동작을 고치는 변경을 어떻게 나눌까?
