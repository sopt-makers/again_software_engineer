## 다시, 소프트웨어 엔지니어

> **Chapter 05**  
> 자동 테스트: 좋은 소프트웨어를 만드는 최고의 습관

---

### 내가 생각하는 핵심 문장 정리

5장은 자동 테스트가 단순히 코드가 잘 동작하는지 확인하는 수단이 아니라, **코드의 품질과 설계를 개선하고 안정적으로 변경할 수 있게 해주는 개발 습관**이라는 점을 강조하는 내용이었습니다. 특히 테스트를 많이 작성하는 것 자체보다는, 무엇을 어떤 수준에서 테스트해야 하는지 판단하는 것이 중요하다고 생각했습니다.

- 테스트를 개선하는 데 집중하면 **코드 품질을 높이고 운영 환경의 문제를 줄이며, 프로젝트에 기여하는 속도를 높일 수 있다.**

- 테스트를 코드보다 먼저 작성하는 것은 말하기 전에 먼저 생각하는 것과 같다. 테스트를 먼저 고민하는 과정은 **구현해야 할 동작을 명확하게 하고 생각을 구조화하는 데 도움**을 준다.

- 테스트는 단순히 기능을 검증하는 것에서 끝나지 않고, **더 나은 코드 설계로 이어질 수 있다.** 또한 잠재적인 결함을 미리 발견하고 유지보수성과 재사용성이 높은 소프트웨어를 만드는 데 도움을 준다.

- 기능을 구현하는 것이 1차적인 목표이더라도, **해당 변경이 전체 시스템에 어떤 영향을 미칠지 함께 고려해야 한다.**

- 테스트는 무조건 많이 작성하는 것이 중요한 것이 아니라, **우리가 작성한 코드의 의미 있는 동작을 검증하는 데 집중해야 한다.**

- 테스트를 개선하는 데 집중하면 코드 품질을 높이고 운영 환경의 문제를 줄이며 프로젝트에 기여하는 속도를 높일 수 있다.
- 테스트를 코드보다 먼저 작성하는 건 말하기 전에 먼저 생각하는 것과 같다. 생각을 정리하고 구조화하는 데 도움을 주기 때문이다.
- 테스트를 작성하다 보면 기능을 검증하게 될 뿐만 아니라 더 나은 코드 설계로 이어진다.
- 테스트는 잠재적인 결함이 문제로 드러나기 전에 미리 발견하게 해주며, 유지보수하기 좋고 재사용 가능한 소프트웨어를 만들도록 도와준다.
- 1차 목표는 기능을 구현하는 것이겠지만, 그 변경이 전체 시스템에 어떤 영향을 줄지 함께 고려해야 한다.
- 테스트 피라미드에서 위로 올라갈수록 테스트 실행 속도는 느려지고, 유지보수 비용은 비싸지며, 깨질 가능성은 커진다.
- 우리가 작성한 코드에 집중해야 하며, 언어 기능이나 프레임워크 코드를 테스트할 필요는 없다.
- 취득 메서드(getter), 설정 메서드(setter), 빌더 메서드, 자동 생성된 데이터 전송 객체처럼 생성된 코드는 테스트하지 말자.
- 비공개 메서드를 직접 테스트하는 일은 피하자. 대신 이런 비공개 메서드를 호출하는 공개 인터페이스에 집중하자.
- 테스트가 외부 서비스에 의존하지 않게 작성하자. 단위 테스트에는 모의 객체를, 통합 테스트에는 테스트 대역을 대신 사용하자.
- 동작을 검증하는 의미 있는 테스트 작성에 집중하고, 코드 실행률은 관심이 더 필요한 코드로 우리를 안내하는 용도로 사용하자.

### 이야기해보면 좋을 내용

현재 메이커스에는 테스트 코드가 충분히 적용되어 있지는 않은 것으로 알고 있는데, 그렇다면 지금 우리 코드에 테스트를 도입한다면 어떤 부분부터, 어떤 종류의 테스트를 적용하는 것이 가장 효과적일지 이야기해보면 좋을 것 같다고 생각했어요.
