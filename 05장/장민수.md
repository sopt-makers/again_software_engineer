# 5장. 자동 테스트: 좋은 소프트웨어를 만드는 최고의 습관

## 핵심 요약

- 자동 테스트는 버그를 찾는 도구이면서 기대 동작을 설명하는 문서, 설계의 피드백, 변경의 안전망이다.
- 단위·통합·종단 간 테스트는 서로 다른 범위의 문제를 검증하며 속도와 비용을 고려해 조합해야 한다.
- 테스트가 코드를 실행했다는 사실과 올바른 동작을 검증했다는 사실은 다르다. Assertion과 시나리오의 의미를 살펴야 한다.
- 테스트 대역은 의존성을 통제하는 데 유용하지만 실제 구성요소의 연결을 검증하는 테스트도 필요하다.
- 테스트를 한 번에 완성하려 하기보다 기능 개발과 버그 수정, 리팩터링 과정에서 지속적으로 축적한다.

## 1. 품질을 습관으로 만들기

좋은 소프트웨어는 출시 직전에 한 번 확인해서 만들어지는 것이 아니다. 구현, 리뷰, 테스트에서 좋은 선택을 반복한 결과다.

자동 테스트 작성은 처음에는 구현 외의 추가 작업으로 느껴질 수 있다. 하지만 코드가 성장하고 요구사항이 바뀔수록 매번 수동으로 전체 동작을 확인하는 비용도 늘어난다.

테스트는 지금의 기대 동작을 기록하고 다음 변경에서 다시 확인할 수 있게 만든다. 작성 비용뿐 아니라 이후의 유지보수와 반복 검증에서 얻는 가치를 함께 봐야 한다.

## 2. 자동 테스트의 네 가지 이점

### 실행 가능한 문서

문서가 부족한 시스템에 합류하면 테스트 이름과 준비 데이터, 실행 대상, 기대 결과에서 동작을 배울 수 있다.

책은 결제 처리 테스트를 예로 든다. 유효한 카드번호 확인, 거래 처리, 특정 결제 수단의 지원 여부를 드러내는 이름은 코드 전체를 읽기 전에 탐색할 위치를 알려준다.

특정 카드 유형에서 실패해야 한다는 테스트가 있다면, 그것은 단순한 예외 코드가 아니라 아직 지원하지 않는 기능의 경계를 보여준다. 정상 동작과 거절해야 하는 동작 모두 문서의 일부다.

### 유지보수성 향상

어떻게 테스트할지 고민하면 책임이 섞인 부분과 강하게 결합된 의존성이 드러난다.

책의 `BlogPostController.publish`는 글 저장, 로그 기록, 구독자 이메일 발송을 한곳에서 처리한다. 이를 테스트하려 하면 데이터베이스와 이메일 등 여러 관심사를 동시에 준비해야 한다.

책은 이 사례를 단일 책임 원칙과 연결해, 각 단계의 책임을 별도 구성요소로 분리하는 개선 방향을 제시한다. 테스트하기 어렵다는 현상은 설계를 검토할 단서가 된다. 단순히 호출하는 의존성이 여러 개라는 이유만으로 설계 결함이라고 판단하기보다, 변경 이유와 책임의 경계를 함께 살핀다.

### 변경에 대한 자신감

기존 기능을 깨뜨릴지 모른다는 불안은 개선과 실험을 주저하게 만든다. 의미 있는 테스트 모음은 리팩터링과 기능 추가 후 기존 동작을 확인하는 안전망이 된다.

테스트가 모든 오류를 막아준다는 뜻은 아니다. 어떤 동작을 검증하고 있는지 알고, 변경과 관련된 시나리오가 충분히 포함되어 있어야 그 결과를 판단할 수 있다.

### 일관성과 반복 가능성

사람은 같은 확인 절차를 반복하면서 단계를 놓치거나 다른 입력을 사용할 수 있다. 자동 테스트는 정해진 조건과 절차를 반복 실행할 수 있어 회귀 확인에 유용하다.

CI에서 변경마다 실행하면 문제를 만든 시점 가까이에서 피드백을 받는다. 운영 이후에 발견하는 것보다 원인과 수정 범위를 찾기 쉬워진다.

## 3. 테스트 피라미드와 검증 범위

책의 그림 5-1은 단위 테스트를 기반으로 하고, 그 위에 통합 테스트와 종단 간 테스트를 두는 피라미드를 보여준다.

| 유형 | 검증 범위 | 장점 | 비용과 한계 |
| --- | --- | --- | --- |
| 단위 테스트 | 격리된 함수나 구성요소의 동작 | 빠른 피드백, 실패 원인을 좁히기 쉬움 | 실제 구성요소 사이의 연결 문제는 놓칠 수 있음 |
| 통합 테스트 | 여러 구성요소가 연결되어 수행하는 동작 | 데이터 접근과 모듈 간 상호작용 확인 | 환경과 의존성 준비가 필요하며 비용이 증가함 |
| 종단 간 테스트(E2E) | 선택한 시스템 경계를 통과하는 전체 시나리오 | 사용자에게 전달되는 흐름의 연결 확인 | 실행이 느리고 환경 영향과 유지보수 부담이 큼 |

피라미드 위로 올라갈수록 실행 시간이 길어지고 실패에 영향을 주는 요소도 늘어나는 경향이 있다. 그래서 모든 검증을 E2E로 해결하면 피드백이 느려지고 실패 원인을 찾기 어려워질 수 있다.

반대로 단위 테스트만 통과한다고 구성요소들이 실제로 함께 동작한다고 보장할 수는 없다. 범위별로 어떤 위험을 확인할지 분담하는 것이 중요하다.

책은 고정된 비율을 정답으로 제시하지 않는다. 복잡성, 기술 스택, 제품의 중요도와 조직의 기준에 맞춰 구성해야 한다.

## 4. 무엇을 테스트하고 무엇을 줄일 것인가

테스트가 많다는 사실보다 검증할 가치가 있는 동작을 확인하는지가 중요하다.

책이 제시하는 기본 방향은 다음과 같다.

- 직접 작성한 사업 규칙과 동작에 집중한다.
- 언어의 기본 기능이나 프레임워크 구현 자체를 다시 검증하는 테스트는 줄인다.
- 단순한 자동 생성 getter·setter·DTO 코드를 수치 확보만을 위해 테스트하지 않는다.
- 비공개 메서드를 직접 호출하기보다 공개 인터페이스에서 관찰할 수 있는 결과를 검증한다.
- 외부 서비스의 상태에 의해 결과가 달라지지 않도록 테스트 범위에 맞는 대역을 활용한다.

옮긴이는 학습, 호환성 확인, 소비자 주도 계약처럼 외부 라이브러리나 서비스를 검증할 필요가 있는 예외도 덧붙인다. 외부 시스템의 구현을 대신 검증하는 것과 우리 시스템이 기대하는 계약을 확인하는 것은 구분해야 한다.

## 5. Coverage: 실행의 지도이며 품질의 판정은 아니다

Coverage는 테스트가 실행한 코드의 범위를 보여준다. 책은 이를 탐험한 구역이 밝혀지는 게임 지도에 비유한다.

| 종류 | 알려주는 내용 |
| --- | --- |
| 행 단위 coverage | 어떤 코드 줄이 실행되었는가 |
| 분기 단위 coverage | 조건문의 어떤 분기가 실행되었는가 |
| 함수 단위 coverage | 어떤 함수가 호출되었는가 |

핵심 사업 로직의 낮은 coverage는 검증의 사각지대를 찾는 단서가 될 수 있다. IDE와 CI에서 보고서를 확인하면 검증을 보강할 위치를 찾을 수 있다.

하지만 메서드를 호출하기만 해도 실행 범위는 늘어난다. 결과가 맞는지 확인하지 않는 테스트는 coverage를 높이면서도 회귀를 놓칠 수 있다.

따라서 임의의 숫자를 채우기보다 다음을 확인한다.

1. 이 테스트가 검증하는 규칙은 무엇인가?
2. 잘못된 결과가 나오면 실패하는가?
3. 중요한 조건과 경계가 포함되어 있는가?
4. 유지보수 비용에 비해 제공하는 보호가 충분한가?

## 6. 테스트 선행과 테스트 후행

### 테스트 선행: Red → Green → Refactor

1. 기대 동작을 표현하는 실패 테스트를 작성한다.
2. 테스트를 통과하는 최소한의 구현을 만든다.
3. 동작을 유지하면서 구조를 개선한다.

먼저 검증할 동작을 정하면 요구사항과 인터페이스를 구체화할 수 있다. 리팩터링 단계에서도 같은 기대 결과를 유지하는지 확인한다.

### 테스트 후행

기능을 구현한 뒤 테스트를 작성한다. 책은 두 접근 모두 가능하며 프로젝트 요구와 팀의 선호에 따라 선택할 수 있다고 설명한다.

어느 쪽이든 예상 결과를 명확히 검증하는 것이 핵심이다. 테스트를 언제 썼는지만으로 품질을 판단하지 않는다.

## 7. Assertion과 테스트 대상 시스템

Assertion은 기대한 조건과 실제 결과를 비교해 성공과 실패를 결정한다. 값의 일치, 실패 여부, 오류 사유 등 검증하려는 계약을 분명하게 표현해야 한다.

SUT(System Under Test)는 현재 테스트하려는 대상이다. 테스트가 준비하는 요소가 많아질수록 무엇을 검증하려는지 먼저 정하는 것이 중요하다.

책의 `Operations` 사례는 덧셈과 뺄셈을 검증한다. 양수뿐 아니라 양수와 음수의 조합, 음수끼리의 연산도 확인해 일반적인 입력 외의 동작을 살핀다.

테스트 구조는 준비 → 동작 실행 → 결과 확인으로 읽을 수 있어야 한다. 이름과 입력, assertion이 함께 기대 동작을 설명해야 문서 역할도 수행한다.

## 8. 모의 객체와 실제 통합을 구분하기

모의 객체는 SUT가 의존하는 구성요소를 통제 가능한 대역으로 바꾸는 방법이다.

책의 `UserService`는 `UserRepository`와 `EmailService`에 의존한다. 단위 테스트에서는 실제 데이터베이스나 이메일 시스템 대신 대역을 제공한다.

- 사용자 이름이 존재하지 않는다는 조건을 설정한다.
- 사용자 등록을 실행한다.
- 저장과 환영 이메일 요청이 이루어졌는지 확인한다.

이 테스트는 지정한 조건에서 서비스가 의존성을 어떻게 사용하는지 확인한다. 실제 데이터베이스에 데이터가 저장되거나 이메일 전달까지 성공했다는 증거는 아니다.

통합 테스트는 여러 구성요소를 실제로 연결해 중복 사용자 거절과 유효한 사용자 등록 등을 검증한다. 전체 구성요소를 대역으로 바꾸면 원래 확인하려던 연결 문제를 검증하지 못할 수 있다.

## 9. 전체 흐름 테스트에서 확인할 것

책의 사용자 등록 예시는 API 요청을 보내 응답을 확인한 뒤, 데이터베이스에서 사용자를 찾아 이메일 값까지 검증한다.

핵심은 응답 성공 여부에만 그치지 않고 요청의 결과가 저장 상태로 연결되었는지 확인하는 것이다. 테스트 전 데이터를 초기화해 이전 실행의 영향을 통제하는 과정도 포함된다.

다만 책의 예시는 `MockMvc`로 서버 측 요청을 시뮬레이션하는 범위다. 실제 브라우저에서 네트워크를 거쳐 동작하는 사용자 여정까지 검증한 것으로 확대해서 해석하지 않는다. 테스트 이름보다 실제로 포함하는 경계를 확인해야 한다.

## 10. AI와 점진적인 테스트 개선

AI는 기존 스타일에 맞는 테스트 초안, 경계 조건 후보, 반복 코드 작성과 가독성 개선을 도울 수 있다.

생성된 테스트도 기대 결과가 요구사항과 맞는지 검토해야 한다. 구현을 그대로 따라 만든 테스트는 구현의 오류까지 정답으로 받아들일 수 있다.

테스트가 부족한 프로젝트는 모든 영역을 한 번에 덮으려 하기보다 현재 변경하는 동작부터 보호한다. 버그를 수정할 때는 재현 테스트가 수정 전 실패하고 수정 후 통과하는지 확인한다.

## 실천

1. 현재 담당한 기능의 핵심 규칙과 실패 조건을 적는다.
2. 기존 테스트에서 실제로 확인하는 assertion을 살핀다.
3. 현재 위험을 가장 명확히 검증할 범위의 테스트를 선택한다.
4. 버그는 재현 테스트부터 작성하고 수정 전후 결과를 확인한다.
5. Coverage 보고서에서 중요한 사각지대를 찾고 의미 있는 검증을 보강한다.

## 토론 질문

1. 빠르지만 대역이 많은 테스트와 느리지만 실제 통합을 확인하는 테스트를 어떻게 조합할까?
2. 어떤 동작은 테스트할 가치가 높고, 어떤 테스트는 유지보수 부담만 늘릴까?
3. Coverage 목표가 의미 없는 테스트를 유도하지 않도록 어떤 기준을 함께 봐야 할까?
4. AI가 만든 테스트가 실제 결함을 발견할 수 있는지 어떻게 검토할까?
