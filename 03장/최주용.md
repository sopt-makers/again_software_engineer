# 사람을 위한 코드 작성법

코드는 의도를 명확하게 전달하여 코드가 수행해야 할 작업을 사람이 파악할 수 있어야 한다. 읽기 쉬우면 유지보수하기도 쉽다.

### 바퀴 재발명 금지

코드를 줄줄이 써 내려가기 전에, 풀어야 할 문제가 이미 해결된 것은 아닌지 잠시 확인해보자.

활용할 수 있는 라이브러리가 있는지 조사해보자. 물론 무분별한 라이브러리 사용은 지양해야 한다. 반드시 해당 라이브러리의 의존관계나 관련된 회사의 정책/절차를 반드시 준수해야 한다.

또한 사용하고 있는 언어를 다시 확인하자. 사용할 수 있는 언어의 기능이 있는가?

애플리케이션 프레임워크도 마찬가지다.

이는 `게으른 프로그래머 정신` 의 연장선이다.

### 간결함의 가치

> 소프트웨어 설계의 목표는, 사람의 지능에 맞게 덩어리로 뭉치거나 조각으로 나누는 것이다. 소프트웨어의 크기는 계속 커지지만, 사람의 지능에는 한계가 있으므로 계속 변경하려면 우리는 지속해서 다른 형태로 끊고 잘라야 한다. - 켄트 백

#### 컴퓨터 과학의 제0법칙

- 응집도 : 사물들이 서로 어떻게 관련되어 있는지를 나타내는 척도, 낮을수록 좋다
- 결합도 : 모듈이나 루틴이 서로 의존하는 정도, 낮을수록 좋다

#### 상속보다는 구성

슈퍼클래스를 만드는 상황에서, 하위 클래스가 반드시 슈퍼클래스에 속하지 않는 새로운 유형의 객체가 등장할 가능성이 있다. 따라서 구성(`composition`)은 상속보다 더 유연하므로 자주 쓰여야 한다.

#### 짧은 메서드 지향

### 코드 주석의 문제

코드에 주석을 많이 다는 것이 좋아 보일 수 있지만, 틀림없이 이는 나쁜 코드 냄새다. 코드 주석은 DRY(`Dont Repeat Yourself`) 원칙을 위반한다.

즉, 코드를 작성한 다음 다시 돌아서서 동일한 내용의 주석을 작성하게 된다.
(주석 사용 여부로 개발자의 경험 수준을 알 수 있는 경우가 많다.)

어떤 작업을 했는지에 대해 문서화를 하는 것보다, 코드 자체를 읽기 쉽게 작성하는 것이 낫다. 주석을 써야겠다고 생각한다면 추상화에 대해서 다시 생각해봐야 하며 메서드나 변수의 이름을 바꿔보는게 낫다.

주석을 작성해야하는 상황이 있긴 하다. 단순하지 않은 일, 단순화할 방법을 찾지 못했다면 주석이 도움이 될 수 있다.

이 때는 `무엇을` 했는지가 아닌 `왜` 했는지에 초점을 맞추어야 한다.

### 테스트를 문서로 사용

좀 더 서술적인 방식으로 작성된 테스트는 코드와 함께 진화하는 `실행 가능한 명세서` 다. 코드를 작성하면서 테스트를 같이 작성하면 자유롭게 리팩토링할 수 있게 되고, 애플리케이션 품질에 대한 확인이 높아진다.

기존 코드에 테스트를 추가하면, 알게 된 코드의 동작 방식을 체계적으로 정리할 수 있다.

> 뭉치고, 끊어지는 코드 덩어리에 대한 명세서, 즉 동작 방식을 테스트에 남기자.

#### 소비자 주도 계약

서비스 제공자가 규약을 일방적으로 정하는 일반 관례와는 달리, 서비스를 사용하는 측에서 서비스 사용 조건을 테스트 형태로 작성해서 주면
제공자는 이 테스트들을 통과하는 한도 내에서 서비스를 변경하는 방식.

→ 하휘 호환성을 유지하면서 서비스를 발전시키는 전략.
