## 3장에서 말하고자 하는 것은...

코드는 컴퓨터가 실행하는 것이지만, **실제로 코드를 읽고 수정하는 것은 사람**이다. 그래서 좋은 코드는 단순히 동작하는 코드가 아니라 다른 사람이 읽었을 때 그 의도와 흐름을 쉽게 이해할 수 있는 코드여야 한다. 특히 실무에서는 내가 작성한 코드를 다른 사람이 수정하거나, 시간이 지난 뒤 내가 다시 수정하는 경우가 많기 때문에 읽기 쉬운 코드를 작성하는 것이 중요하다.
(코드리뷰에서 불필요한 기교를 잡아내자)

사람이 이해하기 쉬운 코드를 만들기 위해서는 코드의 복잡도를 낮추고, 이름만 보아도 역할을 알 수 있도록 적절한 이름을 사용해야 한다. 함수나 변수에 불필요하게 많은 책임을 담지 않고, 하나의 코드가 하나의 역할에 집중하도록 만드는 것도 중요하다. 코드를 짧게 만드는 것 자체가 목적이 아니라, 코드를 읽는 사람이 **자연스럽게 의도를 파악할 수 있도록 만드는 것**이 핵심이다.

또한 코드에는 작성자의 생각과 의도가 드러나야 한다. 주석을 많이 작성하는 것보다 코드 자체가 무엇을 하는지 명확하게 표현되는 것이 우선이며, 코드만으로 설명하기 어려운 이유나 배경이 있다면 주석을 활용해 그 맥락을 남겨야 한다. 결국 좋은 코드는 현재 동작하는 것에서 끝나는 것이 아니라, 다른 사람이 이어서 변경하고 유지보수할 수 있어야 한다.

코드를 작성할 때는 **항상 내가 아닌 다른 사람이 이 코드를 읽는 상황**을 생각해야 한다. 지금 당장은 이해되는 코드라도 시간이 지나거나 다른 사람이 보면 이해하기 어려울 수 있다. 그래서 읽기 쉬운 이름을 짓고, 적절하게 구조화하고, 불필요한 복잡성을 줄이는 작은 선택들이 쌓여 좋은 코드가 된다. 결국 사람을 위한 코드 작성법은 코드를 예쁘게 작성하는 방법이 아니라, **코드를 읽고 수정할 다음 사람의 시간과 노력을 줄이는 방법**이라고 볼 수 있다!

## 인상 깊었던 부분

코드 작성법 뿐만 아니라 코드리뷰에 대한 것도 있어서 전반적으로 협업 잘하는 코드 잘 쓰는 엔지니어가 되는 법을 이야기 하는 장이라고 느껴졌다

> 코드를 작성해 문제를 해결할 수 있다고 해서 문제를 해결하려면 반드시 코드를 작성해야 하는 것은 아니다. 현재로서는, 그리고 아마 앞으로도 AI는 어떤 문제를 해결하는 코드를 쓸 수 있는지와 써야 하는지를 구분하지 못한다.

→ 문제를 해결하기 위해 반드시 새로운 코드를 작성해야 하는 것은 아니라는 점에는 공감했다. 기존 코드를 제거하거나 통합하는 것처럼, 코드를 추가하지 않는 것도 하나의 해결 방법이 될 수 있기 때문이다. 다만 AI가 ‘작성할 수 있는 코드’와 ‘작성해야 하는 코드’를 구분하지 못한다는 부분은 정확히 어떤 의미인지 궁금했다. 이미 AI를 활용하면서 기존 코드를 수정하거나 불필요한 코드를 제거하는 방식으로 문제를 해결하는 경우도 있기 때문에, 책에서 이야기하는 구분의 기준이 무엇인지 생각해보게 됐다. 결국 개발자에게 필요한 것은 코드를 만들어내는 능력뿐 아니라, 애초에 코드가 필요한 문제인지 판단하는 능력일 수도 있겠다는 생각이 들었다.

> 다시 말해, 함수가 무슨 일을 하는지 이해하는 데 얼마나 걸리는가? 메서드 본문을 조사하지 않고도 이름만 읽으면 코드가 무엇을 하는지 바로 이해할 수 있어야 한다. 이 원칙을 따르다 보면 종종 몇 줄, 심지어 단 한 줄짜리 함수가 만들어지기도 한다. '의도'를 명확히 하자.

→ 이 부분에서는 이전에 정훈님께서 공유해준 [Name Your Effects](https://neciudan.dev/name-your-effects) 아티클이 떠올랐다. 당시에도 useEffect 내부의 동작을 직접 읽지 않더라도 이름을 통해 어떤 역할을 하는지 알 수 있도록 기명으로 분리하는 방식에 대해 이야기했는데, 이번 장에서 말하는 ‘의도를 명확하게 표현하는 코드’와 같은 맥락이라고 느꼈다. 결국 좋은 명명은 단순히 변수나 함수의 이름을 정하는 문제가 아니라, 코드를 읽는 사람이 구현을 하나하나 따라가지 않아도 작성자의 의도를 이해할 수 있도록 만드는 일이라는 생각이 들었다. 이전에 읽었던 내용과 연결해서 이해할 수 있어 더욱 인상 깊었다!!

> 형식적이든 아니든, 특정 실천법을 통해 코드 리뷰를 개선할 수 있다. 무엇보다도, 친절해야 한다. 비꼬는 태도는 피하자. 피드백 요청은 아주 스트레스받는 일일 수 있으며, 많은 사람이 비판을 개인적인 일로 받아들인다. 의견을 공유하는 방식이 중요하다. 팀원과 공감하자. 코드 리뷰를 자신의 기술적 전문성을 과시하거나 지엽적인 잡지식을 뽐내는 기회로 삼고 싶은 유혹이 들 수 있지만, 목표는 코드를 개선하는 것이지 기술적 우위를 자랑하는 것이 아니다.

→ 이 부분은 앞으로 코드 리뷰를 할 때 스스로 계속 기억하고 싶은 내용이었다. 예전에 한 프로젝트에서 특정 팀원과 페어 프로그래밍을 하며 코드 리뷰를 정말 많이 받은 경험이 있는데, 당시에는 코드 리뷰 자체가 상당히 부담스럽게 느껴졌다. 그 팀원이 날카로운 말투를 사용했던 것도 아니고 대부분 도움이 되는 피드백이었지만, 취향에 가까운 부분까지 지적받는 경우가 있었고 한 번에 완성도 높은 PR을 올려야 한다는 부담도 컸던 것 같다. 리뷰가 계속해서 쌓이면서 코드를 개선하는 과정이라기보다 내가 **평가**받고 있다는 느낌을 받게 되었던 것 같다.

이 경험을 다시 떠올리면서 코드 리뷰에서는 무엇을 이야기하는가뿐만 아니라 어떻게 전달하는가도 중요하다고 느꼈다. 개선해야 할 부분을 정확하게 짚는 것은 필요하지만, 많은 피드백이 한꺼번에 전달되거나 개인의 선호와 객관적인 개선점을 구분하지 못한다면 리뷰를 받는 사람에게는 큰 부담이 될 수 있다. 결국 코드 리뷰의 목적은 리뷰어의 기술적 우위를 보여주는 것이 아니라 함께 더 나은 코드를 만들어가는 데 있는 만큼, 나 역시 리뷰를 할 때 이 목적을 잊지 않아야겠다고 생각했다!!

## 이야기 나눠보고 싶은 부분

코드 리뷰를 받으면서 막막함이나 두려움을 느꼈던 경험이 있는지 궁금해요. 반대로 리뷰를 받으면서 실제로 많은 도움이 되었다고 느꼈던 경험이나, 좋은 코드 리뷰라고 생각했던 사례가 있다면 함께 이야기해보고 싶습니다!

특히 코드 리뷰에서 **반드시 수정해야 하는 문제와 개인의 취향에 가까운 의견을 어떻게 구분하는지**, 그리고 리뷰어는 어느 정도까지 피드백을 전달하는 것이 적절하다고 생각하는지 각자의 기준을 들어보고 싶어요. 코드의 품질을 높이기 위해 필요한 피드백과 리뷰를 받는 사람에게 부담으로 느껴질 수 있는 피드백 사이의 기준이 무엇인지도 함께 이야기해보면 좋을 것 같습니다!!
