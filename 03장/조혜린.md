### 바퀴 재발명 금지

새 기능을 만들기 전에 **이미 해결된 문제인가?** 부터 확인하자.
프로젝트 내부에 이미 비슷한 코드가 있을 수도 있고 사용하고 있는 언어나 프레임워크에서 같은 기능을 제공하고 있을 수도 있다. 이미 충분히 검증된 라이브러리나 일반적인 해결 방법이 존재할 수도 있다.

- 현재 코드 어디엔가 같은 기능이 이미 구현되어 있는지 확인한다.
- JDK/표준 라이브러리나 기존 프레임워크 기능으로 해결할 수 있는지 확인한다.
- 검증된 오픈소스나 일반적인 패턴이 있는지 확인한다.
- 기존 방식이 오래됐다고 바로 갈아엎기보다, 왜 그렇게 되어 있는지 맥락을 먼저 이해한다.

바퀴를 다시 만들지 말라는 말은 단순히 코드 중복을 줄이라는 의미가 아니다.
기존 코드와 라이브러리를 조사하는 과정 자체가 프로젝트가 어떤 방식으로 문제를 해결하고 있는지 배우는 과정이다.

<img width="1350" alt="Image" src="https://github.com/user-attachments/assets/617011e8-315b-4a9f-8fff-f8b6356efc68" />

코드에는 영원한 정답이 없는 것 같다. 지금은 좋은 구조라고 평가받는 방식도 프로젝트의 규모나 요구사항, 기술의 변화에 따라 나중에는 오히려 불편한 구조가 될 수 있다.

특히 **예전부터 이렇게 해왔으니까**, **원래 이 패턴을 사용하는 게 정석이니까**라는 이유만으로 기존 방식을 계속 사용하는 것은 경계해야 한다. 과거에 좋은 선택이었다는 사실이 지금도 좋은 선택이라는 근거가 되지는 않는다.

그래서 어떤 패턴이나 구조를 적용할 때 이게 모범 사례인지보다 왜 지금 이 상황에서 이 방법을 사용해야 하는지를 설명할 수 있어야 한다고 느꼈다.

### 좋은 코드란

좋은 코드를 판단하기 위해 여러 지표를 사용한다.
(복잡도, 코드 중복률, 테스트 커버리지, 린트 규칙 등)

<br/>

지표가 코드 품질을 확인하기 위한 도구가 아니라 목표 자체가 되면 안된다.

테스트 커버리지 80%를 반드시 달성해야 한다고 정해두면 커버리지 숫자를 올리기 위해 테스트를 작성할 수 있다.
숫자는 좋아졌지만 실제 시스템의 안정성이 좋아졌다고 말할 수 없다.

> 숫자를 낮추는 것 자체가 아니라 그 숫자가 왜 그렇게 나타났는지를 이해해야한다.

### 간결함의 가치

> 낮은 결합도와 높은 응집도

나쁜 예시

낮은 응집도 ex => 알림 기능에 인쇄 로직이 포함되어 있는 것
높은 결합도 ex => 알림 서비스를 변경했는데 인쇄 모듈이 고장나는 것

> 상속보다는 구성

상속은 코드를 재사용하기 쉬운 방법이지만, 상속 관계가 깊어질수록 하나의 코드를 이해하기 위해 부모 클래스의 동작까지 계속 따라가야 한다.
반면 구성은 필요한 기능을 가진 객체를 조합해 사용하는 방식이다. 어떤 기능을 가지고 있는지가 코드에서 비교적 명확하게 드러나기 때문에 관계를 이해하거나 변경하기도 쉬워진다.

> 짧은 메서드 지향

함수 이름을 짓는 것이 유독 어려울 때가 있다.

처음에는 단순히 네이밍을 못해서 그런 것이라고 생각할 수 있지만, 오히려 함수 자체가 너무 많은 일을 하고 있어서 하나의 이름으로 설명할 수 없는 것은 아닌지 확인해볼 필요가 있다.

책에서도 메서드 이름에 and, or, but과 같은 접속사가 필요하거나 이름이 지나치게 길어진다면 메서드가 너무 많은 책임을 가지고 있지는 않은지 살펴보라고 한다.

그래서 앞으로는 함수명이 잘 떠오르지 않을 때 단순히 좋은 이름을 찾는 데 시간을 쓰기보다
**이 함수가 정말 하나의 역할만 하고 있는가?**를 먼저 확인해보면 좋을 것 같다.

<br/>

### 코드 주석의 문제

> 코드에 주석을 ㅁ낳이 다는 것이 좋아보일 수 있지만, 틀림없이 이는 나쁜 코드 냄새이다.

복잡한 코드 옆에 설명을 길게 달면 당장은 이해하기 쉬워질 수 있다. 하지만 코드가 변경되고 주석이 함께 수정되지 않으면 오히려 잘못된 정보를 전달할 수도 있다.

<img width="1328" alt="Image" src="https://github.com/user-attachments/assets/1d90c305-b7fc-4a7f-89cd-5763123ede9f" />

다만 코드만으로는 표현할 수 없는 비즈니스적인 이유, 예외적인 정책, 외부 시스템의 제약처럼 왜 이렇게 작성했는가를 설명해야 할 때는 주석이 필요하다.

이 주석은 복잡한 코드를 설명하기 위해 필요한가, 아니면 코드만으로 알 수 없는 맥락을 남기기 위해 필요한가?를 생각해보면 좋을 것 같다.

<br/>

### 테스트를 문서로 사용

테스트 자체가 하나의 문서가 될 수 있다는 관점이 계속해서 이 책에 나오는데 이 부분이 인상적이다.

일반적인 문서는 코드가 변경된 뒤 함께 수정되지 않으면 실제 동작과 달라질 수 있다지만 테스트는 코드와 함께 실행되기 때문에 구현이 변경되었을 때 영향을 받을 수밖에 없다.

이런 점에서 잘 작성된 테스트는 단순한 설명서보다 현재 시스템이 어떻게 동작해야 하는지를 보여주는 실행 가능한 명세에 가깝다.

특히 처음 보는 기능을 이해할 때 구현 코드부터 전부 읽기보다 테스트를 먼저 보면 어떤 입력을 넣었을 때 어떤 결과가 나와야 하는지와 예외 상황에서 어떻게 동작해야 하는지를 빠르게 파악할 수 있다.

결국 테스트를 작성할 때도 단순히 커버리지를 높이는 것에 집중하기보다

> 이 테스트만 읽어도 이 기능이 어떻게 동작해야 하는지 이해할 수 있는가?

를 생각해보면 좋을 것 같다.

<br/>

### 멋부린 코드 금지

코드는 복잡한 문제를 해결하다 보니 자연스럽게 복잡해질 수 있다. 하지만 문제가 복잡하다는 것과 코드까지 복잡해야 한다는 것은 다른 문제다.

복잡한 문법이나 기발한 표현을 사용하면 코드를 짧게 만들 수 있고, 작성하는 순간에는 더 세련되어 보일 수도 있다. 하지만 다른 개발자가 그 코드를 이해하기 위해 한참을 해석해야 한다면 오히려 유지보수 비용만 커진다. 책에서도 복잡성을 과시하기보다 가능한 한 단순하고 유지하기 쉬운 코드를 작성하는 방향을 강조한다.

> 코드는 내가 얼마나 많이 알고 있는지를 보여주는 수단이 아니라 다른 사람이 얼마나 쉽게 이해할 수 있는지가 더 중요하다.

결국 멋진 코드를 작성하려고 하기보다 뻔하더라도 의도가 명확한 코드를 작성하는 편이 낫겠다라는 생각이 들었다.

<br/>

### 코드 리뷰

코드 리뷰를 할 때 가장 먼저 기억하고 싶은 것은 코드 리뷰의 목적이 상대방보다 내가 더 잘 알고 있다는 것을 보여주는 것이 아니라는 점이다.

책에서도 무엇보다 리뷰 과정에서 친절해야 한다는 점을 강조한다. 코드 리뷰는 누군가의 실수를 찾아내고 지적하기 위한 과정이 아니라, 다른 관점에서 코드를 살펴보고 함께 더 나은 방향을 찾는 과정이다

그래서 리뷰할 때는 사소한 스타일이나 개인적인 취향보다 정말 중요한 부분에 집중할 필요가 있다. 코드가 읽기 쉬운지, 테스트가 적절한지, 기존 인터페이스와 일관성이 있는지, 오류 상황을 고려했는지, 변경으로 인해 예상하지 못한 문제가 생기지는 않는지처럼 실제 품질에 영향을 주는 부분을 보는 것이 중요하다. 아래는 책에서 서술한 기준이다.

- 메서드와 변수 이름은 명확하고 간결한가 ?
- 코드는 읽기 쉬운가? 중복은 없는가?
- 코드에 적절한 로그, 추적, 지표가 있는가?
- 인터페이스가 코드의 나머지와 일관성이 있는가?
- 개발자가 오류가 발생하기 쉬운 형식을 사용했는가?
- 모델이 올바른가?
- 잘못된 추상화를 선택했는가?
