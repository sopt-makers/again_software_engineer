## 2장에서 말하고자 하는 것은?...

실무에서는 새로운 프로젝트를 처음부터 만드는 것보다 이미 존재하는 코드를 읽고 이해하며 수정하는 일이 훨씬 많다. 교육 과정에서는 보통 백지에서 프로젝트를 시작하기 때문에 코드 작성에 익숙해지기 쉽지만, **실제 현업에서는 다른 사람이 만든 코드와 기술 부채, 기존의 결정들 속에서 문제를 해결**해야 한다. 그래서 코드를 읽고 이해하는 능력은 실무에서 반드시 필요한 기본 능력이다.

기존 코드를 이해할 때는 코드를 무작정 처음부터 읽기보다 **먼저 프로젝트가 무엇을 해결하는지, 어떤 구조로 되어 있는지, 주요 도메인과 데이터의 흐름이 무엇인지 파악**해야 한다. 그다음 코드를 직접 탐색하면서 함수가 어디서 호출되는지, 구현은 어디에 있는지, 어떤 코드가 자주 변경되었는지, 테스트에서는 무엇을 검증하고 있는지를 살펴보면 코드의 의도와 구조를 이해하는 데 도움이 된다.

이때 기존 코드를 볼 때는 **내가 생각하기에 이상하다는 이유만으로 쉽게 판단해서는 안 된다.(바보는 나일수도 있었다…)** 당시에는 그 나름의 이유와 비즈니스 상황이 있었을 수 있기 때문에, 먼저 왜 이렇게 만들어졌는지를 이해해야 한다. 결국 기존 코드를 잘 읽는다는 것은 문법을 해석하는 것을 넘어 **코드에 담긴 의도와 맥락을 파악하는 것**이다. 그리고 모든 코드를 한 번에 이해하려 하기보다 필요한 부분부터 조금씩 읽고, 모르는 부분은 찾아보고 질문하면서 이해의 범위를 넓혀가는 연습이 필요하다.

즉, 코드 문해력은 단순히 코드를 읽을 줄 아는 능력에서 끝나지 않는다. 좋은 코드를 읽고 많이 연습하면서 코드의 구조와 의도를 빠르게 파악하는 감각을 길러야 한다. **지름길은 없고! 다양한 코드를 직접 읽어보는 경험**이 쌓일수록 낯선 프로젝트를 이해하는 속도도 빨라진다.

## 인상 깊었던 부분

사실 2장 자체가 흥미로웠다. 그동안 개발 책에서 많이 접했던 내용은 코드를 어떻게 잘 작성하는지에 대한 이야기였는데, 이번 장에서는 반대로 내가 작성하지 않은 코드를 어떻게 읽고 이해할 것인지에 대해 다루고 있었다. 실무에서는 새로운 코드를 작성하는 것보다 이미 존재하는 코드를 읽고 수정하는 일이 많다는 점을 생각하면 오히려 더 현실적으로 느껴졌다!!

> 레거시 코드의 정의는 다양하다. 어제 작성된 코드, 테스트가 제대로 갖춰지지 않은 코드로 정의될 수도 있지만, 그저 자신이 작성하지 않은 코드를 가리키기도 한다.하지만 기존 애플리케이션이 거둔 성과를 폄하해서는 안 된다. 어떤 제품이 다년간 사업 가치를 창출하며 지속해서 투자를 정당화했다면, 이를 인정해야 마땅하다.'코드 유산'이나 '기존 코드'와 같은 더 긍정적인 표현이 좋겠다.

→ 나는 그동안 레거시 코드라고 하면 자연스럽게 **오래되고 잘못된 코드, 결국 언젠가는 바꿔야 하는 코드**라고 생각했던 것 같다. 그런데 레거시라는 말 자체에도 여러 의미가 있고, 그저 내가 작성하지 않은 기존 코드일 수도 있다는 이야기를 보면서 생각이 조금 달라졌다.
지금의 내가 봤을 때 아쉬운 코드라고 해서 당시에도 잘못된 선택이었다고 단정할 수는 없고, 그 코드가 **오랜 시간** 서비스의 가치를 만들어냈다면 그 나름의 이유와 성과가 있었던 것이다. 그래서 기존 코드를 마주했을 때 무조건 레거시라고 부르며 부정적으로 바라보기보다, 왜 이런 모습으로 만들어졌는지 그 당시의 맥락과 히스토리를 먼저 이해해야겠다는 생각이 들었다. **정말 문제가 있어 개선해야 하는 코드와 단순히 오래되었다는 이유로 낯설게 느껴지는 코드를 구분하는 것도 중요할 것 같다...**

> 소프트웨어 고고학!!

→ 낯선 코드를 만났을 때 한 번에 전체를 이해하려고 하기보다, 코드를 둘러싼 흔적들을 하나씩 찾아가며 시스템이 지금의 모습이 된 이유를 추적하는 방식인데, 처음 보는 프로젝트를 어디서부터 살펴봐야 할지 막막했던 경험을 생각하면 **일종의 로드맵**처럼 느껴졌다. 단순히 코드를 위에서부터 읽는 것이 아니라 프로젝트의 구조나 변경 이력, 테스트 등 여러 단서를 통해 코드의 의도와 맥락을 찾아가는 방법이라는 점이 좋았다.

> 테스트는 종종 유저 스토리와 연결되어 업무 처리 절차나 작업 흐름을 이해하는 데 훌륭한 방법이 된다. 시야를 넓혀, 통합 테스트는 사업 요구사항을 충족시키는 데 구성요소들이 어떻게 어울려 동작하는지 알 수 있는 큰 그림을 보여주곤 한다. 전체 업무 절차를 처음부터 끝까지 검증하는 테스트를 찾아보자. 이런 테스트에는 실제 시나리오를 나타내는 설정 코드가 포함돼 있어 시스템이 운영 환경에서 어떻게 동작하는지에 대한 맥락을 제공한다.

→ 테스트에 대한 생각도 조금 달라졌다. 테스트를 단순히 버그를 찾거나 코드가 정상적으로 동작하는지 확인하기 위한 도구로만 생각했는데, 기존 코드를 이해하는 과정에서는 기능이 어떻게 동작해야 하는지를 알려주는 문서처럼 활용할 수도 있었다. 특히 일반적인 문서는 코드와 함께 계속 업데이트되지 않을 수 있지만 테스트는 코드와 함께 실행되기 때문에 현재 시스템의 동작을 이해하는 데 **유용한 단서**가 될 수 있다는 점이 흥미로웠다.

## 이야기 나눠보고 싶은 부분

낯선 코드를 마주했을 때 **각자 코드를 이해하는 방법이나 루틴**이 있다면 소개해보는 시간을 가져도 좋을 것 같아요!

저는 보통 어디서부터 봐야 할지 정하는 것부터 어려울 때가 있는데, 프로젝트 구조부터 보는지, 관련된 컴포넌트나 함수를 따라가는지, Git 이력이나 테스트를 먼저 확인하는지 등 사람마다 코드를 읽는 순서가 다를 것 같아서 궁금합니다.

그리고 코드를 읽을 때 어느 정도까지 파고드는지도 각자 기준이 다를 것 같아요. 모든 구현을 이해하고 넘어가는 사람도 있을 것이고, 현재 작업에 필요한 부분만 추상화해서 이해하는 사람도 있을 텐데, 각자가 생각하는 **‘이 정도면 코드를 이해했다’고 판단하는 기준**도 함께 이야기해보면 좋을 것 같습니다!
