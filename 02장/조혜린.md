### 기존 코드 작업의 어려움

> **도메인을 몰라요**

: 코드가 다루는 업무나 서비스의 개념을 모르면 변수명과 로직을 읽어도 왜 그렇게 동작하는지 이해하기 어렵다. 특히 문서가 충분하지 않은 프로젝트에서는 용어 자체가 장애물이 된다.

> **코드 구조와 스타일이 낯설어요**

: 같은 기능도 팀마다 설계 방식, 패턴, 네이밍, 파일 분리 기준이 다르다. 내가 익숙한 방식과 다르다고 해서 잘못된 구조라고 바로 판단하면 안 된다.

> **코드 품질과 기준이 제각각이에요**

: 기존 코드에는 좋은 패턴과 아쉬운 패턴이 섞여 있을 수 있다. 따라서 기존에 이렇게 되어 있으니 그대로 따라야 한다와 내 방식이 더 좋아 보이니 전부 바꾸자 사이에서 균형이 필요하다.

> **기술 자산의 공백이 있어요**

: 처음 보는 프레임워크, 라이브러리, 디자인 패턴이 등장하면 코드를 읽는 속도가 급격히 떨어진다. 이때는 모르는 부분을 확인하고 학습하면서 읽어야 한다.

익숙한 것에 끌린다 (단순 노출 효과)

따라서 기존 코드를 평가할 때는 먼저 내가 익숙하지 않아서 불편한 것인지, 실제로 유지보수나 기능상 문제가 있는 것인지를 구분해야 한다

### 낯선 코드 접근법

새로운 프로젝트에 들어가 기존 코드를 이해해야 할 때는 곧바로 코드를 읽기보다 **먼저 프로젝트의 맥락을 파악하는 것이 중요하다.**

코드만 보면서 구조를 추측하다 보면 몇 시간이 걸릴 수 있지만 잘 작성된 문서를 먼저 읽으면 프로젝트의 전체적인 구조와 반복적으로 사용되는 패턴을 빠르게 파악할 수 있다.

<aside>

**몇 분 동안 문서를 읽는 것이 몇 시간 동안 코드를 들여다보는 것보다 더 많은 정보를 줄 수 있다.**

</aside>

프로젝트에 문서가 거의 없다면 코드를 이해해가는 과정에서 **직접 문서를 작성해보는 것도 좋은 방법**이다. 문서화하는 과정 자체가 내가 이해한 내용을 다시 구조화하게 만들기 때문에 프로젝트를 더 깊게 이해하는 데 도움이 되고 이후 같은 코드를 접하게 될 다른 개발자에게도 유용한 정보가 된다.

문서를 작성할 때는 처음부터 완벽하고 거대한 문서를 만들기보다 다음과 같은 기본적인 질문에 답할 수 있는 정도로 가볍게 시작하는 것이 좋다.

- 이 서비스는 어떤 일을 하는가?
- 전체적으로 어떻게 동작하는가?
- 어떤 시스템이나 모듈에 의존하는가?
- 애플리케이션은 어떻게 실행하는가?

결국 낯선 코드를 빠르게 이해하기 위해서는 **코드부터 파고드는 것이 아니라, 문서와 팀의 맥락을 통해 전체 그림을 먼저 파악하고 필요한 부분의 코드로 좁혀 들어가는 접근**이 필요하다.

### 소프트웨어 고고학

⇒ 글쓴이는 낯선 시스템을 이해하는 일을 소프트웨어 고고학에 비유한다

1. 화면이나 실제 동작에서 **관심 기능**을 하나 정한다.
2. 그 기능과 **연결된** URL, 라우트, 컨트롤러, 메서드 이름을 찾는다.
3. **호출되는 함수**와 **참조되는 타입**을 따라가며 범위를 좁힌다.
4. 필요하면 브레이크포인트를 걸어 실제 실행 순서를 확인한다.
5. **Git 로그**와 **blame**으로 언제, 왜 바뀌었는가를 확인한다.

### 효과적인 코드 이해 전략

> **IDE를 코드 이해 도구로 사용하자**

: IDE는 단순히 코드를 입력하는 편집기가 아니다. 특히 기존 코드를 읽을 때는 탐색, 관계 파악, 구조 시각화 기능이 큰 도움이 된다.

- **자주 쓰면 좋은 탐색 기능**
  - **`사용처/참조 찾기`**: 이 함수·클래스·변수가 어디에서 사용되는지 확인한다.
  - **`정의로 이동`**: 라이브러리나 내부 구현을 바로 확인한다.
  - **`호출 계층(Call Hierarchy):`** 누가 누구를 호출하는지 흐름을 본다.
  - **`타입 계층(Type Hierarchy)`**: 상속·구현 관계를 확인한다.
  - **`의존 관계/구조 보기`**: 모듈과 클래스 간 연결을 시각적으로 파악한다.

> **테스트는 살아있는 문서다**

: 주석이나 문서는 오래될 수 있지만 잘 관리된 테스트는 이 코드가 어떤 입력에서 어떻게 동작해야 하는가를 구체적인 예로 보여준다.

| **테스트 종류**  | **무엇을 알려주는가**                         | **포인트**                 |
| ---------------- | --------------------------------------------- | -------------------------- |
| 단위 테스트      | 함수·메서드 단위의 구체적 동작                | 입력값, 반환값, 예외 처리  |
| 통합/흐름 테스트 | 여러 컴포넌트가 연결되어 기능이 동작하는 과정 | 실제 업무 흐름과 호출 순서 |
| 경계 조건 테스트 | 잘못된 값이나 극단적인 상황에서의 처리        | 시스템의 제한과 실패 조건  |

### 완성의 길, 연습

> **AI는 어떠한가?**

```
다른 분야와 마찬가지로 소프트웨어 도구도 계속 진화한다.
셀 기반 문서 편집기부터 통합 리팩터링 도구와 인텔리센스(IntelliSense) 코드 자동 완성을 갖춘 IDE에 이르기까지,
코드 작성은 점점 더 쉬워졌다.
물론 작업하는 애플리케이션의 크기와 복잡성 또한 커졌으므로 코딩의 어려움은 큰 차이가 없을지도 모른다!

깃허브 코파일럿(GitHub Copilot)이나 챗GPT(ChatGPT) 같은 생성형 AI의 등장으로
개발자가 곧 대체될 것이라는 주장도 있다.
개발자의 종말에 대한 소문은 코볼(COBOL)부터 4세대 프로그래밍 언어(4GL), 다양한 드래그 앤 드롭 ‘프로그래밍’ 솔루션에 이르기까지
소프트웨어 엔지니어링 수요를 대규모로 줄이는 데 실패한 사례들을 볼 때 과장된 경우가 많다.

이런 도구는 개발자의 개인 도구 상자에서 저마다의 역할이 있다.
예를 들어 GPT에게 코드 조각이 무엇을 하는지 물어볼 수는 있지만 여전히 맥락을 이해해야 한다.
AI는 특정 클래스의 목적을 모르기 때문에 여전히 개발자는 코드를 읽고, 문서를 훑어보고, 동료 개발자와 대화해야 한다.

AI는 아직 전체 기업 코드를 완전히 이해하지 못하며, 환각(hallucination)의 위험은 실재한다.
AI가 도움을 줄 수는 있지만, 궁극적으로는 여러 저장소에 분산된 코드 사이의 미묘한 차이와 관계를 이해해야 하는 쪽은 결국 사람이다.

이 책의 저자 중 한 명인 댄(Dan)은 AI를 사용할 때 사람은 승객이 아니라 조종사여야 한다고 즐겨 말한다. **신뢰하되 검증하자.**

AI는 아무것도 없는 진공 상태에서도 코드를 이해할 수 있지만, 기업의 방대한 전체 코드는 환각 없이 이해하지 못할 수 있다.
현대의 애플리케이션은 종종 여러 저장소에 분산되어 있고 다수의 라이브러리를 활용한다.
개발자인 우리는 AI 도구가 개발을 성공적으로 촉진할 수 있도록 관계와 복잡성을 이해해야 한다.
```

<aside>

위에서 이야기하는 것
: Copilot이나 ChatGPT 같은 생성형 AI가 코드 작성과 설명을 도울 수 있지만, 그것이 코드 이해 능력을 대신하지는 못한다고 본다.

</aside>

- AI가 만든 코드는 일반적인 패턴을 바탕으로 할 수 있어 현재 프로젝트의 맥락과 맞지 않을 수 있다.
- 겉으로는 그럴듯해도 기존 구조, 의존성, 팀의 규칙과 충돌할 수 있다.
- 따라서 AI가 제안한 코드를 받아들일지 판단하려면 결국 사람이 코드를 읽고 평가할 수 있어야 한다.

⇒ AI가 코드를 대신 써주는 시대일수록 생성 능력보다 검증하고 판단하는 능력의 중요성이 더 커질 수 있다.
