# 2장. 코드 문해력 = 실무 기본 능력

## 핵심 요약

- 실무에서는 코드를 작성하는 것보다 기존 코드를 읽고 이해하는 시간이 많다.
- 코드 독해는 사업적 문제, 작성자의 관점, 추상화, 변경 이력을 함께 이해하는 작업이다.
- 문서와 팀원에게서 큰 그림을 얻고, 실제 기능의 실행 흐름을 따라 정신 모델을 구축한다.
- IDE, 테스트, Git 이력은 탐색의 도구이며, 이름이나 지표만으로 동작과 품질을 단정하면 안 된다.
- AI의 설명은 보조 자료로 활용하고 실제 코드, 맥락과 실행 결과로 검증한다.

## 1. 코드 읽기가 기본 능력인 이유

교육에서는 빈 편집기에서 시작해 언어의 문법을 익히는 경우가 많다. 실무에서는 수년에 걸쳐 쌓인 코드와 기존 결정의 제약 안에서 작업한다.

코드를 읽는다는 것은 각 문장의 동작을 해석하는 것에 그치지 않는다. 어떤 문제를 해결하는 코드인지, 어디에서 호출되는지, 어떤 가정을 담고 있는지 이해해야 한다.

AI가 코드를 생성하더라도 독해의 필요는 사라지지 않는다. 직접 작성하지 않은 코드를 검토하고 제품에 통합하려면 그 코드의 의미와 영향을 판단할 수 있어야 한다.

## 2. 기존 코드를 어렵게 만드는 네 가지 요소

### 사업적 문제

문법을 알아도 도메인의 규칙을 모르면 코드가 왜 필요한지 알기 어렵다. 시스템이 누구의 어떤 문제를 해결하는지 먼저 파악해야 한다.

### 이전 개발자의 관점

같은 문제도 서로 다른 패턴, 패러다임, 라이브러리로 해결할 수 있다. 자신의 방식과 다르다는 이유만으로 잘못된 코드라고 판단하지 않는다.

### 추상화의 적절성

모델이 지나치게 일반적이거나, 실제로 다른 개념을 하나로 합쳐 놓았을 수 있다. 코드 구조를 이해하는 것과 그 구조가 문제를 적절히 표현하는지 판단하는 것은 별개의 작업이다.

### 변경의 퇴적층

언어 기능과 개발 관행은 바뀐다. 현재는 불필요해 보이는 코드도 작성 당시에는 제약을 해결하는 선택이었을 수 있다. 긴급 수정과 기능 추가가 겹치며 최초의 의도가 흐려지기도 한다.

따라서 현재의 기준과 작성 당시의 맥락을 함께 살펴야 한다.

### 레거시 코드에 대한 관점

레거시 코드의 정의는 다양하다. 오래된 코드, 테스트가 없는 코드, 자신이 작성하지 않은 코드를 뜻하기도 한다.

기존 제품이 여러 해 동안 가치를 제공했다면 그 성과도 인정해야 한다. 부정적인 평가만 앞세우면 코드에 담긴 경험과 제약을 놓칠 수 있다.

## 3. 인지 편향 경계하기

| 편향 | 의미 | 코드 이해에서의 위험 |
| --- | --- | --- |
| 이케아 효과 | 자신이 만든 결과물에 더 큰 가치를 부여한다. | 자신의 구현을 더 낫다고 여기며 타인의 방식에 불공정한 기준을 적용한다. |
| 단순 노출 효과 | 익숙한 대상에 더 호감을 느낀다. | 처음 배운 언어와 패턴을 기본값으로 삼고 다른 접근을 배척한다. |
| 블럽 역설 | 익숙한 언어 밖의 기능과 표현력을 평가하기 어렵다. | 잘 모르는 기능을 실무에 쓸모없다고 단정한다. |

낯선 코드를 불편하게 느끼는 이유가 실제 결함 때문인지, 단순히 익숙하지 않기 때문인지 구분해야 한다. 이는 동료의 고집을 해석할 때뿐 아니라 자신의 선호를 돌아볼 때도 적용된다.

## 4. 문서와 소통으로 큰 그림 얻기

팀원과 대화하고 README, 위키, 코딩 표준, ADR을 읽는다. 특히 ADR은 코드만으로 알기 어려운 선택 이유와 당시의 제약을 이해하는 데 도움이 된다.

처음에는 다음 질문에 답할 수 있으면 좋다.

- 서비스가 하는 일은 무엇인가?
- 주요 구성요소는 어떻게 상호작용하는가?
- 무엇에 의존하는가?
- 어떤 방법으로 빌드하고 실행하는가?

문서는 오래되었을 수 있으므로 코드와 실행 결과로 확인한다. 문서가 없거나 다르다면 학습한 내용을 가볍게 기록해 다음 개발자의 출발점을 만든다.

## 5. 소프트웨어 고고학: 구조와 행동 연결하기

### 코드의 지형 파악

패키지나 폴더 구조, 도메인 개념, 테스트의 배치를 살핀다. 모놀리스인지 여러 서비스가 나뉜 구조인지도 확인한다.

클래스나 함수의 목적이 불분명하면 사용하는 쪽을 따라 올라간다. 호출부는 어떤 입력과 상황에서 그 코드가 필요한지 알려준다.

### 사용자 행동을 출발점으로 삼기

애플리케이션을 실행하고 화면 요소, 요청 경로, 입력값처럼 검색할 수 있는 단서를 찾는다. 특정 기능이나 버그 하나를 선택하면 탐색 범위를 좁힐 수 있다.

책의 Spring PetClinic 사례에서는 소유자 검색 화면의 템플릿에서 `/owners` 경로를 찾고, 해당 요청을 처리하는 `OwnerController`의 메서드로 이동한다. 중단점을 설정한 뒤 검색을 실행해 실제 호출을 확인한다.

핵심은 **화면에서 관찰한 행동을 코드의 실행 경로와 연결하는 것**이다.

### 정신 모델 구축

정신 모델은 시스템의 구성과 동작을 머릿속에서 설명할 수 있게 만든 이해의 틀이다. 코드를 읽으며 가설을 만들고, 디버거로 실제 값과 경로를 확인하면서 수정한다.

예상과 다른 경로가 실행된다면 이해를 갱신해야 한다. 이름과 들여쓰기, 익숙한 패턴은 단서일 뿐 실제 동작의 증거를 대신하지 못한다.

예외 처리도 살핀다. 너무 넓은 예외를 잡는 코드는 서로 다른 실패 원인을 감춰 흐름을 이해하기 어렵게 만들 수 있다.

## 6. IDE를 탐색과 분석 도구로 활용하기

| 기능 | 확인할 내용 |
| --- | --- |
| 정의로 이동 | 호출 대상의 구현, 타입과 외부 라이브러리 코드를 확인한다. |
| 사용처 찾기 | 어떤 상황에서 구성요소가 호출되고 사용되는지 확인한다. |
| 구현체 찾기 | 인터페이스의 계약이 실제로 어떻게 구현되는지 살핀다. |
| 호출 계층 | 호출하는 쪽과 호출되는 쪽을 연결해 흐름을 파악한다. |
| 타입 계층 | 상속과 구현 관계를 확인한다. |
| 구조 뷰·코드 접기 | 세부 구현을 잠시 숨기고 이름과 시그니처로 역할을 파악한다. |
| 의존 관계 분석 | 모듈과 패키지 간 연결을 살핀다. |
| 자동 검사와 제안 | 오류 가능성과 개선 기회를 발견하고 언어의 관용적인 사용법을 배운다. |

IDE의 제안은 검토할 후보이며 항상 더 나은 선택은 아니다. 실제 의도와 가독성을 고려해 받아들인다.

도구의 모든 기능을 한 번에 익힐 필요는 없다. 책은 매주 새 기능 하나를 익히고 개인 요령 문서에 기록하며 반복해서 사용하는 방식을 제안한다.

## 7. Git 이력에서 얻을 수 있는 맥락

변경 이력은 코드가 어떻게 현재 상태가 되었는지 보여준다.

- 자주 변경된 파일은 어떤 기능과 연결되는가?
- 커밋 메시지에는 어떤 문제와 개선이 기록되어 있는가?
- 현재 코드의 변경을 설명해 줄 사람은 누구인가?

`git log`로 변경 흐름을 보고, `git blame`으로 특정 줄과 관련된 커밋을 찾는다. 이력만으로 이유가 충분히 드러나지 않는다면 동료에게 질문한다.

코드에서 추출한 다이어그램도 구조 파악에 도움이 된다. 다만 구조를 시각화한 자료만으로 사업적 의도나 설계의 모든 이유까지 알 수 있는 것은 아니다.

## 8. 테스트를 문서로 읽기

구현은 코드가 실제로 어떻게 동작하는지 보여주고, 잘 작성된 테스트는 어떻게 동작해야 하는지를 보여준다.

| 테스트에서 볼 요소 | 얻을 수 있는 정보 |
| --- | --- |
| 테스트 이름 | 검증하려는 규칙과 시나리오 |
| 준비 데이터 | 입력 조건과 도메인 상황 |
| 실행 대상 | 어떤 동작과 진입점을 검증하는지 |
| assertion | 기대 결과와 성공 조건 |
| 상호작용 검증 | 저장, 알림 등 다른 구성요소와의 계약 |

### 책의 사례

- 대량 주문 할인 테스트는 일반 고객이라도 일정 규모의 주문에 10% 할인이 적용된다는 규칙을 보여준다.
- 제품 후기 제출 테스트는 제출 결과뿐 아니라 평균 평점 갱신과 관리자 알림이라는 흐름을 보여준다.
- 만료된 신용카드 테스트는 결제를 거절하고 실패 사유를 반환해야 한다는 예외 동작을 보여준다.

정상 경로뿐 아니라 빈 목록, 잘못된 입력, 시간 초과 같은 경계·예외 상황의 테스트도 읽어야 한다. 이런 테스트에는 실제 유지보수 과정에서 발견한 제약과 회귀 방지 지식이 담길 수 있다.

### Coverage의 함정

책에서는 coverage가 92%였지만 결과를 확인하는 assertion이 없어 회귀가 반복된 사례를 소개한다.

Coverage는 실행된 코드의 범위를 알려준다. 기대 결과를 제대로 검증했는지와 요구사항이 옳은지까지 보장하지는 않는다. 테스트를 문서로 읽을 때도 실제로 무엇을 확인하는지 살펴야 한다.

## 9. 점진적으로 이해하고 AI의 설명 검증하기

대규모 코드 전체를 한 사람이 이해하는 것이 목표는 아니다. 지금 다루는 기능의 흐름과 영향 범위를 파악하고, 낯선 부분을 만날 때 같은 과정을 반복한다.

AI는 코드 조각을 설명하는 데 도움을 줄 수 있지만, 다른 저장소와의 관계나 도메인 맥락을 놓칠 수 있다. 설명을 실제 코드, 테스트와 실행 결과에 대조한다. 업무 코드를 입력할 때는 조직의 AI 사용 정책도 고려한다.

독해 능력은 연습을 통해 쌓인다. 관심 있는 오픈소스나 사용하는 프레임워크의 코드를 주기적으로 탐색하고, 시간이 지난 뒤 다른 부분을 읽으며 이해 범위를 넓힌다.

## 실천

1. 기능 하나를 선택하고 사용자 관점의 기대 동작을 적는다.
2. 문서와 테스트에서 도메인 규칙 및 전제를 찾는다.
3. 진입점부터 주요 처리와 결과까지 호출 흐름을 추적한다.
4. 중단점이나 실행 결과로 가설을 확인한다.
5. 확인한 사실, 아직 모르는 부분, 동료에게 물을 질문을 구분해 기록한다.

## 토론 질문

1. 기존 코드가 잘못되었다는 판단을 내리기 전에 무엇을 확인해야 할까?
2. 테스트가 부족한 저장소에서는 어떤 근거로 동작을 이해할까?
3. 수정 전에 필요한 이해의 범위를 어디까지 잡아야 할까?
4. AI의 코드 설명에서 사실과 추측을 어떻게 구분할까?
