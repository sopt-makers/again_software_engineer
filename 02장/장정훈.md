# 2장 코드 문해력 = 실무 기본 능력

> 이전에 코드를 만들던 개발자의 관점에서 문제를 바라봐야 한다.

Feature를 개발하며 이전 개발자들의 코드 위에 내 코드를 올릴때 "왜 이렇게 구현하셨지? 더 가독성 있게, 유지보수 가능하게 작성하실 수 있었을텐데.." 라고 생각한 적이 있다.

이건 짧은 생각이었던것 같다. 그때 당시에 개발 이전에 병목이 있었을 수 있고, 해당 feature를 작은 실험용으로 구현을 하고 사용자의 반응을 보기 위해 간단하게 빠르게 구현했을 수 있다.

그래서 더더욱 이전 개발자들의 관점에서 문제를 바라보려고 노력하고 있다.
<br />

<hr />
"그때는 이런 코드가 유행이었을거야, 그때는 이런 목적으로 구현했겠구나, 시간이 빠듯했겠구나"
<hr />

이 글에서도 똑같이 설명하고 있다.

> 시간에 따라 언어와 모범 사례는 진화하기 때문에, 코드가 작성된 시점의 렌즈를 통해 코드를 바라봐야 한다.

### 오늘의 모범은 내일의 안티패턴이다. - Neal Ford

# 코드 작성은 점점 더 쉬워진다.

이전에는 IDE에서 Tab으로 코드를 추천 해주는것 만으로도 너무 신기하고 대단하다고 생각했다. 그러다 점점 AI가 발전하면서 코드는 너무 잘 짜준다고 생각한다.
<br />
하지만 AI의 한계는 여전히 존재한다. 이번년도 초 학교에서 `인공지능` 강의를 들으며 AI의 작동 원리를 공부했던적이 있다.

정확한 문장은 기억이 나지 않지만 다음과 같은 글 이었던것 같다.

### AI는 정답을 찾아서 알려주는 것이 아니라, 주어진 문맥에서 다음에 올 가능성이 높은 토큰을 계속 예측해 문장을 만들어낸다.

따라서 개발을 할 때 결국 맥락을 이해하는것이 중요하다고 생각이 든다.

이전 장에서 작성했던것 처럼 그때 당시의 개발자의 생각을 이해하고 현재 서비스의 히스토리를 파악하며 개발을 진행해야된다고 생각한다.

그리고 더더욱 hallucination의 위험은 실재하니 개발자가 해당 spec에 대해 정확한 기준을 가지고 있어야 된다고 생각한다.

AI가 짜준 코드를 한번 더 나쁜 코드, 옳은 코드를 비교할 수 있는 능력 즉, 코드 문해력을 높이기 위해 더 코드를 많이 보고, 더 이해하기 위해 공부해야될것 같다.
